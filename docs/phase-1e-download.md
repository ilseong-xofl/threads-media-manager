# 다운로드 버튼·게시글 회차·명시적 복구

2026-09-22 현재 구현 계약이다. 버튼 한 번의 회차 다운로드에 저장 상태 조회·오류 및 비정상 종료 후 명시적 재개·동일 라이브러리 재연결·DB 백업과 복원을 추가했다. Mac 자동·합성 자료 통합 검증을 완료했다. [검증 기록](download-recovery-verification.md)의 범위이며 Windows 배포 준비 완료를 뜻하지 않는다. 검증 범위와 남은 확인은 [다운로드 복구·관리](download-completion-plan.md)에 정리한다.

## 화면과 종료

- 수집 목록에는 첨부가 하나 이상이고 모든 원본 첨부가 검증된 로컬 파일로 연결된 게시글만 표시한다. 일부 저장 게시글은 완료 목록에 넣지 않는다.
- `다운로드 (n)`은 연결한 폴더 전체의 미완료 게시글 수다. 검색·계정 필터와 독립적이며 재개 대상도 없고 0개면 비활성화한다. 대상이 있을 때 약한 강조 효과를 표시하고 동작 줄이기 설정을 존중한다.
- 재개 가능한 기존 배치가 있으면 상단 버튼과 토스트에 `이어서 다운로드`를 제공한다. 로컬 복구만 가능한 상태는 `파일 상태 확인`을 제공한다. 별도의 준비·재계획 패널은 없다.
- 진행 중 버튼 숫자는 마지막 목록 기준이며 상단 중앙 토스트가 게시글·파일·회차 진행과 대기 시각을 보여준다. 작업 종료 뒤 목록과 버튼 수를 갱신한다.
- 토스트는 전송·검증·파일/회차/계정 대기 동안 유지한다. 정상 완료는 `다운로드 완료`를 3초간 표시한다. 오류·보류·복구 안내는 X로 직접 닫으며 X는 작업 상태나 중단 기록을 바꾸지 않는다.
- 수동 중지 버튼은 제공하지 않는다. 활성 다운로드의 정상 창 닫기·앱 종료는 차단하고 완료 후 종료하도록 안내한다. 강제 종료 등 비정상 중단은 다음 실행에서 상태를 확인한다.
- 카드의 반복 저장 수·저장 상태 필터는 제거한 상태를 유지하고 기존 게시글·등록글 ZIP 내보내기는 별도로 제공한다.

## 시작과 회차 정책

`startDownload()`는 main의 `startAll()`과 Python `command: batch`를 호출한다. renderer가 URL이나 임의 계획을 보내지 않는다. 같은 루트의 수집 잠금을 배치 전체 동안 유지하며 로컬 실행기의 기존 전송 함수를 공유한다.

계정명 순서, 계정 안 오래된 게시글 순서, 첨부 순서를 시작 시 고정한다. SQLite `download_batch`에는 원본 참조·해시·대상 ID·정책·회차·진행 위치를 기록한다. 다운로드 계획에 원문 캡션이나 서명 URL 자체를 복제하지 않는다. 진행 중 새 자료를 자동 추가하지 않는다.

같은 계정의 남은 첨부 35–45개를 게시글 전체 단위로 묶고 마지막 회차는 35개 미만도 허용한다. 파일 수를 맞추려고 게시글을 쪼개거나 다른 계정을 앞당기지 않는다. 주소 없음·원본 미확정 등 시작 전에 받을 수 없는 게시글은 보류 수와 이유로 남긴다. 실제 전송 오류를 사전 보류로 바꾸어 다음 게시글로 넘어가지 않는다.

파일 저장·검증 후 3–10초, 회차 후 60–120초, 계정 후 10–30초를 적용한다. 완료 파일·진행 위치·경계 대기는 같은 트랜잭션에 기록하고 마지막 회차·계정의 대기도 다음 실행에 남긴다. 서버 Retry-After를 포함한 조건 중 가장 늦은 허용 시각을 따른다. 재개로 대기를 재추첨해 단축하거나 전송 시간을 완료 후 대기에서 차감하지 않는다.

무응답 30초·파일 시도 총 600초, 시각 역행 검사, 허용 호스트·redirect·파일 검증과 첫 오류 전체 중단을 유지한다. 다운로드 일일 횟수 제한은 없다. 배치 전체에 단일 파일의 총 시간 제한을 적용하지 않으며 main은 유효한 진행 이벤트 사이의 실행기 응답을 감시한다.

## 조회·복구·재개

| 동작                                  | 원격 전송               | 상태 변경                                                                  |
| ------------------------------------- | ----------------------- | -------------------------------------------------------------------------- |
| 앱 시작·새로고침·폴더 연결의 `status` | GET 0                   | 라이브러리 원본 DB·잠금·부분 파일을 변경하지 않고 상태 조회                |
| `파일 상태 확인`의 `recover`          | GET 0                   | 이미 받은 파일의 로컬 복구. 재전송·중단 해제 없음                          |
| `이어서 다운로드`의 `resume`          | 검증된 기존 남은 대상만 | 로컬 복구 후 허용된 중단 사유·기존 배치·최신 원본·대기를 검증하고 실행     |
| 새 `다운로드`의 `batch`               | 새 유한 계획의 대상     | 기존 운영 상태를 먼저 검사. 기존 오류를 지우거나 새 계획으로 우회하지 않음 |

비정상 종료의 WAL·journal이 있으면 상태 조회는 임시 DB 복사본에서 확인하여 라이브러리 바이트를 보존한다. 종료가 확인된 다운로드 전용 잠금은 조회 시 그대로 두며 명시적 복구에서만 처리한다. 활성 수집·활성 다운로드·소유자 미상 잠금은 해제하지 않는다. 빈 라이브러리의 조회만으로 DB를 만들지 않는다.

명시적 재개는 먼저 `running/staged` 등 로컬 저장 경계를 복구한다. 근거가 맞는 staged 파일은 추가 GET 없이 완료할 수 있다. 실패·중단된 첨부는 동일 미디어 ID에 새 작업 ID와 새 `.part` 경로를 만들어 처음부터 받는다. 바이트 단위 Range 이어받기는 없다. 이전 작업·부분 파일·요청 이력과 중단·계획 이력은 보존하고 `job_attempts`로 새 시도와 연결한다. 완료 파일은 그대로 제외하며 과거 실패를 현재 미완료 작업으로 다시 집계하지 않는다.

중단 해제는 재개 가능한 사유를 검증한 명시적 요청에서만 허용한다. 완료 파일 손상·라이브러리 불일치·미완료 삭제 복구·DB 복원 후 이력 확인 필요 상태는 재개로 우회하지 않는다. 첫 재실패도 전체 중단이며 자동 재시도는 없다. 앱 열기·시간 경과·새 Excel·새 URL이 중단을 자동 해제하지 않는다.

## Excel 변경과 기존 대상 보존

수집기의 당일 Excel 교체나 다음 날 Excel 추가로 원본이 바뀔 수 있다. 진행 중 예상 밖 변경은 중단하며 이후 `이어서 다운로드`에서 최신 원본을 다시 읽는다. **기존 배치의 대상만 재검증하며 별도의 재계획 UI는 없다.**

캡션·원본 참조·URL이 갱신돼도 기존 계정·게시글·첨부 수·순서·종류의 연결이 유효해야 한다. 첨부 충돌이나 기존 대상 누락은 차단하고 명시적인 앱 삭제 기록만 제외 근거로 인정한다. 새 게시글은 기존 회차에 편입하지 않으며 이후 별도의 다운로드에서 계획한다. 기존 회차의 잔여가 작아져도 완료 대상을 재요청하거나 신규 게시글로 채우지 않는다.

401/403으로 거절된 동일 URL 해시는 원본이 다시 나타나도 재요청하지 않는다. 같은 대상에 대한 새로 수집된 유효 URL을 검증해야 하며 앱이 수집 플러그인을 실행하거나 대체 URL을 추측하지 않는다. 일반 증분 수집이 기존 URL을 반드시 갱신하는 것도 아니다. 429·서버 대기는 저장된 허용 시각 이후의 명시적 재개에서만 처리한다.

## 설정의 라이브러리 관리

설정은 main의 현재 연결 폴더를 별도로 조회한다. 마지막 정상 목록이 남아 있거나 목록 읽기에 실패해도 설정의 대상이 이전 snapshot 경로로 바뀌지 않는다. 다른 쓰기 작업과 유지관리를 동시에 실행하지 않으며 유지관리 중 정상 종료 요청은 진행 중인 작업의 완료를 기다린다. 완료 후 목록과 다운로드 상태를 갱신한다.

- **재연결:** 전체 수집 폴더를 옮긴 뒤 새 위치를 연결하고 실행한다. DB·미디어 marker의 동일 UUID와 로컬 파일을 확인한 뒤 DB 루트만 갱신한다. 기존 미완료 작업·부분 파일·대기·중단·요청은 유지한다. 파일 이동이나 누락 원본 복원 기능은 아니다.
- **DB 백업:** 네이티브 저장창에서 일관된 SQLite 백업을 `.sqlite`로 저장한다. 다운로드·등록·댓글 등 DB 정보는 포함하지만 이미지·영상·수집 Excel은 포함하지 않는다. 수집 폴더도 별도로 보관해야 한다.
- **정상 DB 복원:** 같은 라이브러리 백업을 선택하고 확인한다. 현재 DB를 `state/backups/`에 먼저 자동 보관한 뒤 등록·댓글 정보를 복원한다. 현재 다운로드·요청·대기·중단·삭제·편집본·작업 시도 이력은 보존한다.
- **유실·손상 DB 복원:** 필요한 파일과 백업의 동일성을 검증하고 백업 시점의 전체 DB로 복원한다. 손상 DB와 sidecar가 있으면 별도 보관한다. 백업 이후 이력을 알 수 없으므로 `database_restored`로 다운로드를 보류하며 일반 재개·파일 상태 확인으로 해제하지 않는다.

다른 앱·다른 라이브러리·지원하지 않는 DB를 덮어쓰지 않는다. 백업·복원·재연결은 CDN 요청이나 수집 실행을 하지 않으며 미디어와 Excel을 백업 파일에서 복구한다고 안내하지 않는다.

## 검증 상태

합성 라이브러리·가상 시계·모의 전송으로 기존 회차 정책과 오류 후 GET 0, 재개 전 GET 0, 완료 파일 재요청 0, 새 시도·과거 부분 파일·요청 이력 보존, 원본 재검증과 신규 게시글 미편입, URL 거절 이력·대기·시각 역행을 검증하는 회귀를 추가했다. 강제 종료 WAL 상태 조회와 로컬 복구, DB 복원 보류 우회 차단도 검증 범위다.

유지관리 회귀는 일관된 DB 백업, 정상 DB의 운영 이력 보존, 현재 삭제 기록 존중, 손상·유실 DB의 전체 복원과 자동 보관, 동일 UUID 재연결, 잠금·경로·receipt·중복 실행·대화상자 취소·종료 대기를 다룬다. 자동 검사와 Electron 화면의 종료 차단·설정 접근·백업/복원 결과·중단 상태·토스트 유지를 확인했다. 구체적인 테스트 수와 확인 범위는 별도 검증 기록에 남긴다.

이번 검증은 실제 사용자 자료의 추가 CDN 다운로드나 재수집을 수행했다는 뜻이 아니다. API 관련 기능은 다음 단계이며 Windows 실제 기능·설치·자동 업데이트 검증과 배포는 별도 잔여 작업이다.

# Threads API 연결·게시·통계

2026-09-28 사용자 결정에 따른 구현 계약이다. Phase 2의 로컬 초안과 별개로 실제 API 게시를 제공한다. 수집 플러그인·Excel·기존 state.db 구조는 유지한다. 2026-09-29 현재 기능 개발과 Mac의 실제 혼합 원글·텍스트 댓글 각 1건 및 통계 수신 검증을 완료했다. 최신 전체 검사와 Windows 잔여 작업은 [체크포인트](checkpoint-2026-09-29.md)를 따른다. 아래 날짜별 검증 기록은 단계 당시의 범위를 보존한다.

## 계정과 저장

- 설정에서 장기 사용자 **토큰만** 입력한다. 현재 토큰의 저장된 만료 시각이 없을 때 main이 `/debug_token`을 호출하고, `is_valid`·`user_id`·`expires_at`을 검증한다. `/me`의 사용자 ID 일치도 확인한 뒤 Meta가 반환한 Unix 초 단위 `expires_at`을 ISO 시각으로 바꿔 암호화 저장하고 사용자 시간대로 표시한다. 유효기간·발급일·만료일을 사용자에게 입력받거나 앱 등록일부터 만료를 추정하지 않는다.
- 만료 시각은 토큰에 연결된 값이다. 저장된 유효한 값이 있으면 상태 조회·재시작·같은 토큰 재입력에서 재사용하고, 다른 토큰으로 교체할 때 새로 조회한다. 기존 저장 토큰에 만료 시각이 누락된 경우 한 번 조회해 보완한다. 조회 실패 시 값을 추정하거나 기존 파일을 덮어쓰지 않으며 계정 사용을 차단하고 재등록을 안내한다.
- `debug_token`은 입력한 토큰을 `access_token`과 `input_token`에 사용한다. 이 방식에는 해당 앱의 Threads 테스터 사용자 토큰이 필요하다. 일반 외부 사용자를 받는 배포에서는 동일 앱의 앱 액세스 토큰으로 검사하는 서버 구성이 별도로 필요하다. 앱 비밀 키를 로컬 앱에 넣지 않는다. 권한 부족·만료·불명확한 응답은 연결 오류로 표시한다.
- 이번 버전은 게시 대상 계정 하나를 연결하며 교체·해제를 지원한다. 계정 교체가 과거 게시 이력을 삭제하거나 다른 계정의 글을 다시 게시하게 만들지 않는다.
- Threads 사용자 토큰과 파일 서버 연결 정보는 Electron safeStorage로 암호화한 앱 userData 파일에 각각 보관한다. 저장한 인증 정보와 미디어 URL은 renderer에 반환하지 않는다. OS 암호화 실패·파일 손상은 사용자 토큰 저장 차단이며 평문 대체·초기화는 없다.
- 게시 이력과 통계도 userData에 보관한다. 라이브러리 DB 백업 복원이 API 게시 이력을 되돌리지 않는다. 게시 연결 키는 라이브러리 UUID + 원글 key + Threads 계정 ID다.
- 앱 시작·절전 복귀·실행 중 주기 검사에서 토큰 만료가 30일 이내이면 갱신한다. 갱신 API 제약과 중복 실행을 고려해 시도 간격을 제한하며, 실패 시 유효한 기존 토큰을 보존한다. 갱신 성공 시 해당 요청의 `expires_in`으로 새 만료 시각을 계산해 저장하며 `debug_token`을 반복 호출하지 않는다. 만료·철회는 재등록으로 안내한다. 앱/PC가 꺼져 있는 동안은 실행하지 않는다.
- 기존 토큰의 insights 권한은 실제 연결 후 통계 조회로 확인한다. 부족할 때만 사용자가 권한을 포함한 토큰을 재발급한다. 앱에 App Secret을 저장하지 않는다.

## 미디어 전달

- 미디어는 독립 파일 서버 `https://tfs.ilscp.net`의 `/api/uploads`에 Bearer 인증과 multipart `file`로 전송한다. 서버가 반환하는 공개 파일 URL을 Threads에 전달한다. 개발자 AWS 키와 S3 환경설정은 앱 실행 경로에서 사용하지 않는다.
- Threads 계정 바로 아래의 파일 서버 설정에서 관리자가 발급한 `tfs1.` 연결 코드 전체를 입력한다. 입력과 저장 버튼은 한 줄이며 코드 교체·연결 해제를 지원한다. 모든 성공·실패는 공통 중앙 상단 토스트를 사용한다.
- 연결 코드는 버전·고정 서버 주소·사용자별 업로드 토큰을 담는다. main에서 형식과 대상 주소를 검증하고 별도 `file-server.json`에 OS 암호화 저장한다. 임의 서버·리다이렉트는 허용하지 않는다. renderer에는 서버 주소와 저장 시각만 반환하며 저장한 토큰을 다시 채우지 않는다.
- 저장은 로컬 형식 검사와 암호화 보관이다. 업로드 없는 인증 조회 API가 없으므로 저장 시 원격 연결 성공으로 표시하지 않고 `저장됨`으로 표시한다. 실제 사용 가능 여부는 업로드 시 확인하며 철회·비활성 코드는 오류 토스트로 안내한다. 저장·교체·해제만으로 업로드나 Threads 게시를 실행하지 않는다.
- 파일은 main에서 스트리밍 전송하며 자동 재시도하지 않는다. 반환 URL의 origin·경로·만료 시각·종류·크기를 검증하고 로그·renderer·게시 이력에는 저장하지 않는다. 게시 작업 중 연결 코드 교체·해제를 막는다.
- 원본·편집본·개발 AI 생성본 중 저장된 초안의 순서를 그대로 고정한다. 소유권·revision·파일 크기·SHA-256을 검증한 별도 임시 복사본만 전송한다. 원본 파일은 변경하지 않는다.
- API 게시 한도(본문 500자, 첨부 최대 20개)는 전송 전에 확인한다. 로컬 초안의 기존 100개/10,000자 계약은 유지한다. 지원하지 않는 미디어는 이유를 표시하고 전송 전에 차단한다.
- 파일 URL은 업로드 완료 후 1시간 동안 접근 가능하다. 서버가 시작 시 및 3시간 간격으로 만료 파일을 삭제한다. 앱은 원격 삭제 요청을 보내지 않으며 게시 성공·실패 후 로컬 전송용 복사본만 정리한다. 사용하지 않는 S3 모듈과 AWS SDK는 2026-09-29 소스 정리에서 제거했다. 과거 사용자 S3 설정·저널 파일은 읽거나 삭제하지 않는다.

## 게시와 복구

- 저장된 등록 글의 API 업로드 → 대상 계정·본문·첨부 수 확인 → 임시 업로드 → 컨테이너 생성/처리 확인 → publish → 새 게시글 ID 영속 저장 순서다.
- 등록 상세의 댓글 정보 아래에는 같은 구분선 형태의 `API 업로드` 영역을 두고 기존 안내·계정·게시 이력을 표시한다. 연결 계정의 원글 게시 성공과 원격 ID가 확인되면 등록 목록에서는 `등록 완료 → 댓글 완료(등록 시) → 세로 구분선 → 다운로드` 순서로 표시하고, 상세에서는 등록한 미디어 제목 오른쪽에 완료 배지를 표시한다. 파일 서버 전송만 완료되거나 실패·결과 불명·댓글만 성공한 경우에는 표시하지 않는다. 로컬 초안을 수정해도 기존 게시 이력은 유지되며 툴팁에 게시 계정을 표시한다.
- API 업로드를 누르면 확인 단계부터 상세화면 전체에 불투명한 잠금 레이어와 중앙 로딩 카드를 표시한다. 마우스·키보드·ESC·바깥 클릭으로 상세를 조작하거나 닫을 수 없다. main이 제공한 실제 진행 단계에 따라 정보 확인·확인 대기·준비·이미지/영상 업로드·Threads 미디어 확인·게시·결과 저장·마무리 안내를 표시한다. 완료·취소·실패 뒤에는 기존 상세로 돌아오고, 성공한 경우 `등록 완료` 배지와 `게시글 등록 완료` 이력이 표시된다. 성공·실패 알림은 공통 토스트를 사용한다.
- 게시 이력이 있으면 API 업로드 제목 아래의 계정명은 숨기고 해당 이력 안에서 한 번만 표시한다.
- API 요청 전에 작업 이력을 저장하고 컨테이너 ID와 게시 단계를 순서대로 기록한다. 처리 상태 확인은 최대 5분, 분당 1회 기준이다. 게시 응답이 불명확하거나 게시 직후 저장 실패 시 재게시하지 않고 `확인 필요`로 남긴다.
- 같은 원글·대상 계정에 성공한 게시 또는 결과 불명 작업이 있으면 새 게시를 차단한다. 결과 불명은 상태 확인 및 사용자가 제공한 실제 Threads ID의 계정/내용 검증으로 연결한다. 임의 자동 재게시가 없다.
- 댓글은 로컬에 저장한 캡션과 링크를 줄바꿈으로 합쳐 **같은 라이브러리·계정·원글의 API 게시 성공 ID**를 `reply_to_id`로 지정해 직접 답글로 게시한다. 수집 원글이나 다른 댓글에 연결하지 않는다. 댓글은 별도 버튼으로 실행하며 미디어를 재업로드하거나 완료 직후 통계를 조회하지 않는다. 직접 답글 연결과 Threads 화면의 최상단 고정은 별개이며, 이 앱은 댓글 표시 순서를 보장하지 않는다.
- 댓글 API 업로드도 전체 상세 잠금 레이어를 사용하며 댓글 정보 확인·확인 대기·준비·처리·게시·결과 저장·마무리 단계를 표시한다. 댓글에는 이미지/영상 업로드 문구나 첨부 개수를 표시하지 않는다. 완료·취소·실패 후 잠금을 해제한다.
- 원글과 댓글의 같은 계정·원글에 대한 게시 성공 및 원격 ID가 확인되면, 상세와 목록의 초록 `등록 완료` 오른쪽에 보라색 `댓글 완료` 배지를 표시한다. 저장만 한 로컬 댓글, 실패·결과 불명, 다른 계정·원글의 이력에는 댓글 배지를 표시하지 않는다. 성공 뒤 댓글 버튼은 `댓글 완료`로 비활성화하고, 이후 로컬 댓글 수정과 무관하게 실제 게시 이력을 유지한다. 결과 불명 댓글도 자동 재전송하지 않는다.
- 게시 중 수정·삭제·폴더 변경·일반 종료를 차단한다. 비정상 종료 후 원격 게시 여부가 불명확하면 사용자 확인을 요구한다.
- 코드 검증은 모의 API로 수행한다. 실제 계정 게시·저장소 업로드와 Windows 배포 검증은 별도로 기록한다.

## 통계

- 설정의 최근 게시글 통계에는 조회 버튼·안내·마지막 조회 시각만 표시하며, 게시글별 캡션·수치 목록은 표시하지 않는다. 개별 수치는 등록 상세의 게시 이력에서 확인한다. `지금 조회`를 누르면 설정 전체를 불투명 레이어로 덮고 중앙 로딩과 `통계 조회 중`을 표시한다. 완료·실패·취소까지 버튼·키보드·ESC·중복 조회를 차단한 뒤 해제하며 결과는 토스트로 안내한다. 자동 백그라운드 조회에는 이 수동 조회 레이어를 띄우지 않는다.
- 게시글 목록 API를 사용하지 않는다. 앱에서 업로드 성공 후 저장한 ID 중 연결 계정의 최신 원글 5개를 대상으로 한다. 댓글 게시 작업은 5개 대상에 포함하지 않는다.
- `/{id}/insights?metric=views,likes,replies`로 한 글의 조회수·좋아요 수·댓글 수를 한 번에 조회한다. 정상적인 5개 갱신은 5회 요청이다. 댓글 본문 조회는 이번 범위에서 제외한다.
- 앱을 시작할 때 오늘 조회한 기록이 없으면 기존 게시글의 통계를 백그라운드에서 한 번 조회한다. 앱을 계속 켜 두면 PC 현지 시각 오전 10시에 조회하며, 시작 시 또는 수동으로 이미 오늘 조회했다면 건너뛴다. 절전 복귀는 실행 중 일정으로 처리한다. 수동 조회는 언제든 가능하며 동시 요청은 하나로 묶는다.
- 게시 완료 경로에서는 통계를 조회하지 않는다. 실행 중 예약 조회는 해당 날짜 오전 10시까지 게시된 글만 대상으로 하므로, 그 시각 이후 새 글을 등록해도 직후 주기 검사에서 통계를 조회하지 않는다. 상세의 게시 시각 옆에 `(매일 오전 10시에 자동 갱신됩니다.)`를 표시하고 통계는 실제 조회된 수치가 있을 때 표시한다.
- 값은 조회 시점의 누적 수치다. 실패·미제공을 0으로 바꾸지 않는다. 마지막 정상 수치·조회 시각·오류를 유지한다. 최근 5개에서 빠진 글은 마지막 값만 보존한다.

## 파일 서버 연결 절차

1. 관리자가 파일 서버에서 사용자를 추가하고 연결 코드를 발급한다. 사용자 이름은 한글을 사용할 수 있다.
2. 로컬 앱의 설정 → Threads 계정 아래 → 파일 서버에 연결 코드 전체를 붙여넣고 저장한다.
3. 저장한 뒤에는 서버 주소와 `저장됨` 상태를 표시한다. 사용자 비활성화·코드 재발급 여부는 실제 업로드 시 확인한다.

- 댓글 전송용 미디어는 없으며 임시 전송 폴더도 남지 않았다. 게시 이후 원글 통계 갱신 시각은 기존 값으로 유지되었고 별도 통계 조회를 실행하지 않았다. 화면 재로딩 후 댓글 완료 상태와 재등록 차단을 확인했다. main 전체 재시작과 Windows 검증은 이번 실제 시험에 포함하지 않았다.

## 2026-09-29 컴퓨터 이전

DB 백업 시 해당 라이브러리의 게시 완료·댓글·결과 불명·통계 이력을 `state/publication-transfer.json`에 보관한다. 작업 폴더 전체를 옮긴 뒤 폴더 연결·DB 복원에서 새 PC의 암호화 저장소로 합친다. 기존 게시 성공·결과 불명 상태를 오래된 복사본으로 되돌리거나 자동 재게시하지 않는다. API 토큰과 파일 서버 연결코드는 포함하지 않으며 사용자가 새 PC에서 다시 입력한다. 이전 파일은 라이브러리 DB와 별도여서 DB 복원만으로 최신 원격 게시 이력을 되돌리지 않는다. [컴퓨터 이전 절차](database-maintenance.md)를 따른다.


## 2026-09-29 게시 ID에서 실제 글 열기

- 게시 완료된 원글·댓글의 게시 ID는 기본 브라우저로 여는 링크 형태로 표시한다. 클릭 시 main이 현재 작업 폴더와 연결 계정의 성공 이력을 확인하고 해당 API ID의 공식 `permalink`를 읽는다. 숫자 API ID를 공개 게시물 shortcode로 추정해 주소를 만들지 않는다.
- renderer는 로컬 게시 이력 ID만 전달한다. main은 응답 ID·게시 계정과 HTTPS Threads 게시물 경로를 검증한 뒤 OS 기본 브라우저로 연다. 조회·브라우저 실패는 공통 토스트로 알리며 기존 게시 성공 이력·본문·미디어는 변경하거나 재게시하지 않는다. 기존 게시 이력도 별도 데이터 마이그레이션 없이 사용한다.
- 실제 주소는 클릭할 때 조회하므로 게시 작업 자체에 추가 대기를 넣지 않는다. 계정 연결이 만료되면 다시 연결한 뒤 사용하며 조회 중 중복 클릭과 계정 교체는 막는다.
- 공식 [문제 해결 문서](https://developers.facebook.com/documentation/threads/troubleshooting?locale=en_US)는 컨테이너 상태를 **1분에 한 번, 최대 5분** 조회할 것을 권고한다. [게시 문서](https://developers.facebook.com/documentation/threads/posts?locale=en_US)의 **게시 전 평균 30초 대기**는 완료 시간 보장이나 30초 재조회 주기를 뜻하지 않는다. 2026-09-29 원문을 확인했으며 현재 `IN_PROGRESS` 이후 60초 재조회 간격을 유지한다. 10초·20초로 변경하지 않는다.

# CDN 다운로드 조사와 대응 가이드

조사·설계 반영일: 2026-09-21. **플러그인은 수집 전용이며 다운로드는 로컬 앱이 담당한다.** 검증된 파일 하나 파일럿을 `local-runtime/`으로 옮겨 보존하고 앱·배치 기능 완성으로 표시하지 않는다. 실제 검증 이력은 [진행 기록](progress.md)을 따른다. 앱 회차·사용자 안내는 [다운로드 대기열 정책](download-queue-policy.md)의 후속 설계다. 미완성 배치 초안은 별도 임시 경로에 보존하고 90회 정책은 적용하지 않는다.

사용자 결정으로 현재 다운로드에는 일일 횟수 제한이 없다. 과거 파일럿1회/24시간 상한은 제거했으며 redirect0회·대기·첫 오류 중단은 유지한다. 현재 구현은 [로컬 실행기 계약](local-download-runner.md)을 따른다.

## 1. 조사 결론

Instagram 미디어 CDN의 이미지·영상 GET이 403으로 실패한 보고가 있다. 서명 만료가 명시된 사례와 원인이 밝혀지지 않은 사례를 구분해야 한다. 403만 보고 IP 차단으로 기록하지 않는다.

이번에 검토한 원문에서는 직접 CDN GET의 429 또는 일정 다운로드량 때문에 IP가 차단됐음을 입증할 사례를 확보하지 못했다. API 조회의 429를 CDN 차단 사례로 대체하지 않는다. 이것은 CDN에 요청 제한이 없다는 결론도 아니다. Instagram 사례를 Threads에 그대로 적용되는 임계값으로 간주하지 않는다.

쿠키·Authorization 헤더를 보내지 않는다는 설계는 로그인 자격증명을 직접 보내지 않는다는 뜻이다. 요청 URL과 서명·접근 검증 정보까지 없어지는 것은 아니므로 이를 익명성이나 계정 영향 없음의 보장으로 해석하지 않는다. 현재 검토한 자료로는 Threads CDN 서명이 다운로드 사용자의 로그인 계정을 식별하는지, 계정 제재에 연결되는지도 확정하지 못했다.

**차단이 발생한다면 IP 차단뿐이고 확률이 낮다는 종전 설명은 근거 부족으로 정정한다.** [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)는 제한 대상의 식별 방식과 요청 집계 범위를 고정하지 않는다. URL 만료·서명 거절과 요청량 제한·IP 차단은 별개이며 응답 코드만으로 서로 대체하지 않는다. 검토한 공식 자료에서는 Threads CDN의 IP 차단 확률이나 안전한 파일 수를 확보하지 못했다.

35–45개 묶음·1–2분 회차 휴식·완료 후 3–10초 대기는 시험할 초기 운영값이다. 묶음을 줄여도 대기 시간이 짧아져 전체 요청 속도는 기존안보다 높아질 수 있으므로 더 안전해졌다고 판정하지 않는다. 무작위 대기 자체도 탐지 회피나 차단 방지를 보장하지 않는다. 첫 오류에 앱 다운로드 전체 중단·서버 대기 준수·성공 파일 재다운로드 방지·요청 이력 보존을 함께 적용한다.

## 3. 로컬 앱 실행기와 계정별 운영 기준

플러그인은 개인 Codex 계정의 로그인된 내부 브라우저로 수집하고 JSONL·Excel·기준 표시를 저장한다. 요청마다 계정당 새 미디어 원글 최대 2건이 기본이며 같은 날 재요청할 수 있다. 수집 가드는 유지한다. 다운로드 명령·state.db·앱 중단 상태에는 접근하지 않는다. 앱은 별도 사용자 요청으로 검증된 Excel을 읽고 다운로드를 진행하며 Threads 페이지/API로 수집하지 않는다.

활성 수집과 다운로드는 루트의 공통 `_work/collector.lock`으로 겹치지 않게 한다. 소유자·토큰을 확인하고 타 실행 잠금을 임의 제거하지 않는다. 앱 단순 열기·마지막 정상 화면 조회는 잠금을 독점하지 않는다. 앱이 오류를 기록하고 작업을 종료하면 잠금은 해제하되 DB 중단 상태는 보존한다. 나중에 별도 요청한 수집은 자체 가드·잠금 조건에 따라 가능하며 다운로드 오류로 자동 금지하지 않는다.

앱 시작·명시적 새로고침·재개에서 확정 원본을 안정 읽기·hash 검증한다. 검증한 유한한 계정·게시글·첨부·원본 버전·정책을 계획으로 고정하고 진행 중 새 Excel을 자동 편입하지 않는다. 전송 직전 원본이 바뀌었으면 앱 다운로드를 중단한다. 새로고침으로 새 실행을 채택해도 기존 실패·중단·예산을 지우거나 자동 재시작하지 않는다.

| 항목 | 기준 |
|---|---|
| 계정 내 순서 | 앱에서 확인한 미완료 게시글을 오래된순으로 처리. 다른 계정과 묶음을 섞지 않음 |
| 동시 전송 | 1개, 파일·회차·다운로드 계정 간 대기 |
| 회차 | 같은 계정의 남은 첨부 35–45개가 되는 온전한 게시글 묶음 |
| 마지막 묶음 | 계정 내 마지막은 35 미만 허용. 다른 계정 자료로 채우지 않음 |
| 요청 기록 | 전송 전 SQLite 기록, 일일 횟수 제한 없음 |
| 누적 집계 | 앱 로컬 실행기가 만든 최근 24시간 요청. 실패·redirect·수동 재시도 포함 |
| 첫 오류 | 앱 다운로드 전체 즉시 중단·미완료. 뒤의 파일·회차·계정 다운로드도 중단 |
| 재개 | 중단 원인·원본·정책·계획·서버 대기 확인 후 명시적 이어하기 |
| 소유자 | 앱 로컬 실행기만 state.db·media 갱신, renderer/main에 중복 전송 엔진 없음 |

초기 운영값은 파일 저장·검증 완료 후 무작위 **3–10초**, 회차 종료 후 **60–120초**, 다운로드 계정 종료 후 **10–30초**다. 파일 간 대기를 전송·저장·검증 시간에서 차감하지 않는다. 허용 redirect의 다음 GET에도 요청 간 대기와 서버의 더 긴 Retry-After가 적용된다. 경계에서 한 번 정한 시각을 보존하며 중첩 조건 중 가장 늦은 시각을 따른다.

다운로드 일일 횟수 제한을 두지 않는다. 과거1회/24시간 설정과90회 제안은 적용하지 않는다. 유한한 대상 계획·파일/회차/계정 대기·redirect 제한·첫 오류 중단을 유지한다.

GET·실패 GET·redirect hop·수동 재시도는 각각 요청 이력으로 남긴다. 실제 전송 전에 기록하며 실패·중지·종료로 되돌리지 않는다. 기록 실패 시 전송하지 않는다. 요청 개수로 다음 파일이나 회차를 막지 않는다. 서버 대기시간 미상이면 완료 시각을 약속하지 않는다.

앱의 state.db에 다운로드 계획·회차·시도·원본 참조·파일 연결·요청 기록·정책·예약·소비·중단·최소 재개 시각을 보관한다. 새 계정·JSONL·URL·업데이트·앱 재시작으로 초기화하지 않는다. 시계 역행 시 기록을 비우지 않는다. 원문 캡션·등록일·전체 서명 URL은 DB에 복제하지 않는다.

다운로드 실패로 검증된 Excel·Excel·수집 기준을 되돌리지 않는다. 앱은 다운로드 복구를 위해 수집을 자동 실행하지 않는다. 앱 시작·새로고침과 새 배치 전 cleanup-source는 source_not_ready·attachment_not_ready인 작업 없는 불완전 수집 글만 post_deletions로 논리적으로 삭제한다. 게시글별 캡션·첨부·URL이 완전하면 상위 수집 실행이 중단/partial이어도 정상 대상으로 유지하며 과거 잘못된 download_exclusions도 해제한다. jobs·부분/다운로드 파일·AI 생성본·등록·편집이 있으면 원본이 나중에 불완전해져도 보호한다. 이 정리는 Excel·수집 기준·원본 해시를 바꾸지 않고 HTTP 요청·파일 삭제 없이 cleanedPosts를 안내한다. 실제 전송 실패는 글과 완료/부분 파일·계획·이력·대기를 보존하고 명시적으로 재개하며 수집 정리로 대신 처리하지 않는다. 다운로드 완료는 선택 원본에 수집된 첨부를 저장한 뜻이며 수집 partial을 complete로 승격하지 않는다. 정리한 불완전 글 수는 `cleanedPosts`, 정상으로 확인해 제외를 해제한 글 수는 `releasedPosts`로 구분한다.

## 4. 오류별 진단과 복구

오류 본문은 이미 받은 응답에서 최대 8KiB만 확인하고 네트워크 추가 진단 요청은 하지 않는다. 전체 본문을 저장하지 않고 인식한 오류 토큰만 기록한다. 실제 응답 hostname, `request_stage=cdn_get`, HTTP status, Content-Type, redirect hop, 원본 참조와 URL hash를 기록한다. IP 차단은 별도 근거 없이 표시하지 않는다.

| 응답 근거 | 분류 | 다음 동작 |
|---|---|---|
| URL signature expired가 명시됨 | `url_expired` | 전체 중단·미완료. 같은 주소 재시도 중지, 새 관찰 주소 필요 |
| Bad URL hash / url signature mismatch가 명시됨 | `signature_rejected` | 전체 중단·미완료. 후보 URL 보존 여부 점검, 쿼리 재작성·추측 금지 |
| 본문 불명인 401/403 | `access_denied_unknown` | 전체 중단, 원인 미확정으로 표시. 인증·IP 원인을 추정하지 않음 |
| 429 | `rate_limited` | 전체 중단, 유효한 Retry-After 적용, 사용자 검토 전 자동 재개 금지 |
| 404/410 | `url_unavailable` | 전체 중단·미완료. 다음 항목 진행 없음, 원문 삭제 여부는 미확정 |
| 503 + 유효한 Retry-After | `server_unavailable` | 대기열 중단, 최소 대기 시각 보존 후 사용자 재개 |
| 그 외 HTTP 오류·네트워크/5xx/timeout | `transfer_failed` | 첫 오류에 전체 중단·미완료. 자동 재시도 없음 |
| 200이지만 HTML/예상 밖 응답/제한 화면 | `unexpected_response` 또는 `access_denied_unknown` | 모두 전체 중단·미완료, 파일 저장 성공 처리 금지 |
| 파일 검증·크기·redirect·원본·디스크·DB 오류 | 해당 단계의 오류 코드 | 전체 중단·미완료. 이미 검증해 저장한 파일은 보존 |

진단 분류는 복구 방법을 정하기 위한 것이며 **어떤 다운로드 오류든 첫 발생에 앱 다운로드 전체를 중단한다**. 실패 파일을 건너뛰어 다음 게시글·회차·계정 다운로드로 가지 않는다. 오류 게시글과 앱 다운로드 실행은 미완료, 앞서 완료한 게시글·파일과 확정된 수집 Excel·기준 ID는 보존한다. 추정 만료시각만으로 `url_expired`라고 확정하지 않는다. 파일 signature/길이 검증 실패도 같은 중단 규칙을 따른다.

최신 결과 Excel을 다시 읽었어도 같은 URL hash라면 401/403 또는 명시적인 로그인·접근 차단으로 거절된 후보를 새 작업으로 재시도하지 않는다. 새 후보를 얻었다면 원본 연결과 정책을 재검증하고 사용자가 다시 선택할 수 있다. 주소 변경은 전역 중단 해제가 아니다. 429는 URL 자체의 영구 거절로 기록하지 않으며 최소 대기·사용자 검토·명시적 재개 후 같은 URL을 다시 시도할 수 있다. 이 요청도 간격을 지키고 요청 이력에 남긴다.

앱 로컬 실행기의 CDN 다운로더와 Electron은 새 주소를 얻으려고 Threads 페이지/API에 접속하지 않는다. 플러그인의 정상 수집은 로그인된 내부 브라우저의 렌더링된 DOM 범위이며 CDN 실패를 이유로 자동 재수집하지 않는다. `재확인 필요` 항목에 계정·게시글 ID·원문 링크를 보여준다. 기존 일일 증분 수집은 과거 실패 글을 자동으로 다시 방문하지 않으므로, 같은 수집을 한 번 더 실행하면 주소가 갱신된다고 약속하지 않는다. 별도로 허용된 정상 브라우저 DOM 재확인에서 새 후보를 결과 Excel에 확정해야 한다. 현재 스킬의 예산·프로필 화면 범위에서 확보할 수 없으면 미해결로 둔다.

쿼리 일부 제거·oe 변경·다른 CDN 호스트 대입·무작위 헤더 변경은 사용하지 않는다. 브라우저 쿠키/세션을 복사하거나 IP/프록시를 바꿔 제한된 요청을 계속 보내는 기능도 도입하지 않는다. 이번에 확인한 만료·서명·미상 403을 그 방법으로 해결할 수 있다는 근거가 없다.

## 5. Retry-After와 중단 유지

[RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)는 429를 요청량 제한으로 정의하지만 식별 대상이나 집계 범위를 고정하지 않는다. 따라서 429도 IP 차단으로 단정하지 않는다. [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)에 따라 Retry-After의 초 단위 값과 HTTP 날짜 형식을 모두 처리한다.

- 유효한 값이 있으면 그 시각 전에는 사용자 재개도 막는다. 값이 없거나 잘못됐으면 `서버 대기시간 미상`으로 남기고 파일 간 대기 3–10초가 지났다는 이유로 자동 재개하지 않는다.
- 3xx에 Retry-After가 있으면 redirect의 다음 GET에도 최소 대기를 적용한다. 대기 중 전체 시도 timeout에 걸리면 중단하며 우회 전송하지 않는다.
- 시각이 지났다는 사실은 재개 신호가 아니다. 사용자가 확인하고 기존 계정의 미완료 회차에 남은 첨부 전체를 다시 확인한 뒤 이어간다. 완료한 파일은 다시 받지 않으며 앱이 수집을 호출하지 않는다. 나중의 별도 수집 요청 여부와 앱 중단 해제는 별개의 판단이다.
- 새 다운로드·URL 갱신·앱 재실행으로 제한 상태를 해제하지 않는다. 401/403의 거절 후보는 기존 주소로 반복하지 않고, 새 후보/원인 확인 후 명시적으로 중단 상태를 해제한다. 429는 최소 대기 조건을 충족한 뒤 명시적 재개가 필요하다.

## 6. 개인별 자료와 요청 집계 범위

멤버는 개인 Codex 계정·브라우저 로그인·로컬 JSONL·Excel을 사용하고 앱이 자기 PC의 state.db·미디어를 관리한다. 로그인 정보나 사용자 DB를 배포물에 넣지 않는다. 플러그인은 다운로드 DB를 읽거나 쓰지 않는다. 중앙 서버·공동 로그인·사내 통합 예산을 전제로 하지 않는다.

앱의 요청 통계는 그 실행기가 발생시킨 CDN 요청만 센다. 횟수 제한은 아니다. 같은 공인 IP를 쓰는 다른 멤버 PC, Codex 수집 브라우저, 다른 앱의 트래픽을 합산하지 못한다. 개인 Codex 계정마다 다른 IP나 별도 네트워크 허용량이 보장되지 않는다. 중앙 서비스 없는 단계에서 사내 전체 IP의 안전 요청량을 보장하지 않는다.

같은 PC·수집 루트의 공통 잠금은 활성 수집과 다운로드의 충돌을 막지만 다른 멤버 PC까지 잠그지는 않는다. 동일 네트워크 초기 검증은 멤버별로 순서대로 한다. [Instaloader의 집계 한계 설명](https://instaloader.github.io/troubleshooting.html#too-many-requests)도 동시 앱과 재시작 전 요청을 추적하지 못하는 가정을 명시하지만 그 수치를 CDN 허용량으로 가져오지 않는다.

## 7. 구현 완료 전 검증

실제 CDN에 오류를 유도하지 않고 모의 HTTP 응답과 가상 시계로 먼저 검증한다.

- CDN 403 만료·서명 오류·불명 응답을 구분하고 모두 추가 GET 0회.
- 429, 302→429, 503+Retry-After, 302+Retry-After 및 초/날짜/미상 값의 최소 대기·중단 보존.
- 원본/정책 모순이면 전송 전 중단. 같은24시간 안의 연속 요청을 일일 횟수로 막지 않음.
- 전송 전 요청 기록과 실패/redirect/재시도 이력 보존. 정책 이관·종료·시계 역행에서도 손실 없음.
- 첫 HTTP·timeout·HTML 200·파일 검증·디스크/DB 오류에 앱 전체 다운로드 중단, 다음 요청 0회, 성공 파일 보존.
- 35–45첨부 게시글 비분할·계정 마지막 35 미만 묶음·3–10초·60–120초·10–30초 경계와 재시작 보존.
- 중단 뒤 추가 첨부·HEAD·원격 미리보기·자동 재시도·자동 브라우저 수집 0회.
- 401/403 거절 후보가 새 원본에도 같은 URL hash로 있으면 자동 재시도하지 않음. 429는 최소 대기와 명시적 재개를 별도로 검증.
- 활성 수집/다운로드는 공통 잠금으로 겹치지 않음. 단순 앱 조회는 잠금 미독점, 플러그인은 state.db 미접근.
- 다운로드 오류 후 별도 사용자 수집은 자체 가드에 따라 진행 가능. 새 Excel·새 URL은 앱 중단 해제·자동 재개·소비량 초기화를 일으키지 않음.
- 진행 중 원본 변경은 앱 다운로드 중단. 이후 명시적 새로고침에서 검증하고 성공 파일이나 기존 미완료 계획을 자동 삭제하지 않음.

문헌 조사에서는 개인 계정·열린 Threads 탭·실제 CDN 파일을 요청하지 않았다. 이 가이드의 차단 방지 효과나 성공률을 측정한 결과는 아니다. 기존 파일럿 검증, 로컬 앱 미구현, 임시 배치 초안 중단 상태를 구분해 보고한다.

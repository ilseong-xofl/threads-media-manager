# 1D 앱 다운로드 최소 기능

2026-09-21: Electron에서 파일 하나의 준비·시작·진행률·중지·저장·로컬 미리보기 갱신을 연결했다. 배치 회차는 1E이며 지금 버튼 한 번은 파일 한 개다. 사용자 결정으로 개발용24시간1회 상한과 화면의 요청 잔여량 표시를 제거했다. 실제 앱에서 남은18개를 순차 처리해 이미지19개·영상1개, 합계20개 전부 저장·검증했다.

## 실행 흐름

1. 계정 필터에서 계정을 고르고 `다음 파일 확인`을 누른다. 계정이 하나면 자동으로 그 계정을 사용한다. 오래된 미완료 게시글의 첨부 순서대로 다음 한 파일을 고른다.
2. 계정·게시글 ID·첨부 순서·종류와 저장된 대기 시간을 확인한다. 이 단계는 원본·DB를 읽기만 하며 DB 초기화·잠금 생성·DNS·GET·HEAD가 없다.
3. `파일 1개 다운로드`를 누르면 같은 원본 해시·실행·대상을 다시 확인하고 작업을 만든다. 전송 전 요청을 SQLite에 기록하고, 수신·형식 검증·UUID 저장을 완료한 뒤 목록과 미리보기를 갱신한다.
4. 첫 오류는 중단 상태를 보존한다. 자동 다음 파일·재시도·재수집은 없다. 중지나 앱 종료는 worker에 취소를 전달하고 종료를 기다린다. 진행 중에는 폴더 변경과 원본 새로고침을 막는다.

원문과 서명 URL은 Excel에서만 읽는다. renderer에는 CDN URL·원본 해시·작업 계획·DB 경로를 전달하지 않는다. Main이 고정한 프로젝트 worker만 실행하며 좁은 IPC와 기존 격리/CSP를 유지한다. SQLite는 기존 라이브러리를 사용하고 완료된 과거 `source_type=jsonl` 파일도 재전송 없이 연결한다.

## 중단과 복구

`로컬 저장 복구`는 검증된 staged 파일을 확정하거나 전송 중 끊긴 작업을 interrupted로 기록한다. 요청 소비·UUID·기존 파일·중단을 유지하며 GET이나 중단 해제를 하지 않는다. 오류 원인 해결과 명시적 재개 UX는 후속 범위다.

비정상 종료로 잠금이 남으면 명시적 복구에서만 download-runner 소유·토큰 형식·죽은 프로세스 여부·동일 잠금 파일을 확인한 뒤 처리한다. 수집 잠금, 살아 있는 프로세스, 확인할 수 없는 잠금은 보존한다. 복구끼리는 별도 짧은 잠금으로 직렬화한다. 복구 중 다시 강제 종료돼 복구 잠금 자체가 남으면 수동 확인이 필요하며 자동 제거하지 않는다.

Python worker는 부모 감시와 stdin 종료/취소를 함께 사용한다. Main은 결과를 읽더라도 worker가 완전히 종료된 뒤 DB를 다시 읽는다. 정상 취소가 끝나지 않으면40초 뒤 worker를 종료하며 다음에는 명시적 로컬 복구가 필요할 수 있다.

## 개발 환경

Node/pnpm/Electron/Forge/Webpack/React는 1C 환경을 유지했다. 앱과 Python 테스트는 `TMM_PYTHON` → 프로젝트 `.venv` → 시스템 Python 순으로 선택한다. Python3.11 이상과 Pillow12.3.0, 영상 검증용 PATH의 ffprobe가 필요하다.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r local-runtime/requirements.txt
pnpm start
pnpm check
```

현재 Mac 검증은 제공된 Python3.12.14/Pillow12.3.0을 프로젝트 `.venv`의 system-site-packages로 연결했다. 의존성 파일은 코드와 분리하고 `.venv`는 Git/포맷/린트에서 제외한다. Windows는 `.venv/Scripts/python.exe`를 선택하도록 구현했지만 실제 실행과 런타임 번들은 1G에서 검증한다. 기존 로컬 앱의 로그인·서비스·DB 연결은 사용하지 않는다.

## 검증 범위

- lint/typecheck/format, TypeScript31개·Python185개 오프라인 테스트. 새 테스트는 준비 단계 무변경, 원본 변경 차단, 중복 시작 방지, 소비량·첫 오류·중지 보존, staged 복구, 실제 Python 프로세스 강제 종료 후 WAL/잠금 복구를 포함한다.
- Mac Electron 합성 자료 검증: 준비 버튼 → 시작 버튼 → 진행 표시 → 저장1/2 → 로컬640px 이미지 로드. 빠른 중복 클릭에도 작업1개·모의 소비1회, renderer 예외0·원격 요청0. 임시 전송기를 개발용 Python 실행 경로로 주입했고 제품에는 모의 전송 플래그를 넣지 않았다.
- 실제 사용자 자료: 게시글10·첨부20·저장 JPEG2개. 상한 제거 후 앱 버튼으로 HTTP GET1회·200 image/jpeg, 767×795·94,380bytes 이미지를 추가 저장했다. Pillow verify/load·SHA-256·DB 완료·로컬 미리보기와 저장2/2 표시를 확인했다. 기존 비DB9파일의 SHA-256과 기존 작업/첨부/요청 행을 보존했으며 새 작업1개·요청1개만 추가됐다. 준비 단계에서 추가 GET0, HEAD0, 수집0, 자동 재시도0이다.

현재 `local-download-v2`에는 다운로드 일일 횟수 제한이 없다. 과거1회/24시간 값은 개발용 설정이었으며 사용자 요청으로 제거했다. 기존 정책 이관은 요청·작업·UUID·중단·대기 보존과 실패 시 원자적 rollback을 검증했다. 같은24시간 안에서도 파일 사이 대기가 지나면 다음 파일을 받을 수 있다. 실제 영상 전송·35–45첨부 회차·Windows 설치/업데이트 완료를 의미하지 않는다.


## 현재 수집 자료 전체 다운로드

사용자의 전체 다운로드 요청으로 기존2개를 보존하고 남은18개(이미지17·영상1)를 앱의 단일 다운로드 명령에 순서대로 전달했다. 시작 전에 전체 대상을 고정하고 Excel hash를 각 파일 전송 전 확인했다. 파일 완료 후 저장된3–10초 대기를 모두 지켰으며 마지막 회차75.112초·계정22.126초 대기를 next_allowed에 보존했다. 실제 다음 요청은 이전 파일 완료로부터3.418–10.234초 뒤 시작했으며 모든17개 파일 경계에서 저장된 허용 시각 이후였다. 범위 차이는 준비/검증/앱 갱신 시간이며 대기를 전송 시간에서 차감하지 않았다.

HTTP18회 추가/총20회·모두200, HEAD/자동 재시도/재수집0회다. 요청당 무응답30초·파일 시도 총600초는 실행기 기본값 그대로 적용됐고 오류·시간 초과는 없었다. 전체20파일 크기·SHA-256, 이미지19개 Pillow verify/load, 영상1개 ffprobe를 확인했다. 영상은H.264·720×960·2.9초·152,902bytes다. Mac 앱에서19개 이미지가 열리고 영상의 재생 시간이 증가함을 확인했으며 저장20/20·renderer 원격 요청0·예외0이다. 기존 비DB10파일과 기존 작업·요청·UUID는 보존됐다.

이번 검증에서 전체 다운로드 버튼이나 범용 회차 UI를 새로 구현하지 않았다. 고정된 현재 자료를 기존 명령으로 모두 처리했으며1E 제품 통합은 별도 구현 범위다. Windows 실제 실행은 아직 미검증이다.

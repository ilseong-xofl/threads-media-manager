# 로컬 게시본의 모바일 전송

## 2026-10-20 보낸 등록본의 댓글 동기화

- 댓글을 저장할 때 그 글에 휴대폰이 아직 게시할 수 있는 등록본(게시 대기·게시 시작·원글 완료)이 있으면, 로컬 저장 전에 서버 `POST /api/v1/publications/:id/comment`로 등록본 댓글을 먼저 바꾼다. 서버 반영이 실패하거나 거절되면 로컬 댓글도 저장하지 않는다. 보내지 않았거나 회수·만료된 글은 로컬에만 저장한다.
- 휴대폰이 그 댓글 게시를 시작했거나 이미 등록한 댓글은 수정할 수 없다(서버 `COMMENT_LOCKED`, 화면 안내). 휴대폰은 댓글 실행을 시작한 뒤 댓글을 다시 읽으므로 시작 전의 PC 수정이 반영된다.
- 게시 대기 중에도 댓글은 수정할 수 있고 본문·미디어는 계속 잠근다. 파일 전송 중이거나 보류된 전송이 있으면 댓글도 잠근다. 전송 후 7일이 지난 등록본에 반영하면 휴대폰 목록에서는 보이지 않는다고 안내한다. 댓글 삭제 기능은 없다.
- 관리자/API를 먼저 배포해야 한다. 이전 API에서는 보낸 글의 댓글 저장이 실패한다.

## 2026-10-20 등록 카드 게시 뱃지

- 등록 탭 카드의 다운로드 버튼 왼쪽 `등록 완료`·`댓글 완료` 뱃지를 휴대폰 게시 결과로 다시 표시한다. 등록 탭이 보일 때(상세를 닫을 때 포함)와 새로고침할 때 서버 `GET /api/v1/publications/statuses`로 라이브러리 전체를 한 번 조회하고, 같은 `postKey`·`draftCreatedAt` 초안에만 표시한다.
- 조회 실패 시 이전 표시를 유지하고 오류를 띄우지 않는다. 예전 PC 직접 게시 이력의 뱃지는 그대로 표시한다. 휴대폰에서 게시한 결과는 다음 조회 때 반영된다.

- 관리자/API 업데이트를 먼저 적용해야 한다. 실제 Meta 요청 중단 지시는 계속 유지한다.

## 사용자 흐름

1. 기존 수집·편집·직접 작성으로 로컬 등록 글을 준비한다. 본문과 별도 댓글·링크를 먼저 저장한다.
2. 등록 상세에서 **모바일로 보내기**를 누른다. 기존 상세는 유지하고 전송 창에서 본인이 등록한 계정을 오래된 등록순으로 보여주고 첫 계정을 기본 선택한다. 원하는 다른 계정으로 바꿀 수 있으며 전송 버튼은 사용자가 직접 누른다. 전송 가능한 계정이 없으면 등록 상세의 보내기 버튼을 비활성화한다. 앱 이름·계정 이름·첨부 수·댓글 유무를 확인한다.
3. 저장된 본문·댓글·미디어 순서의 사본을 만든다. PC에서 필요한 변환을 마친 파일을 S3로 직접 전송한다. API 인스턴스에는 JSON과 완료 확인 요청만 보낸다.
4. 서버가 모든 파일을 검증하고 확정하면 게시 대기로 표시한다. 새 게시본의 게시 기한은 서버 전송 완료 시각부터 7일(168시간)이다. 기존 게시본의 기한은 변경하지 않는다. 파일 전송 완료를 Threads 게시 완료로 표시하지 않는다.
5. 파일 전송 대기·모바일 게시 대기 또는 전송 보류가 남아 있으면 **모바일로 보내기**를 비활성화한다. 게시 시작 전에는 **회수**한 뒤 로컬에서 수정·재전송한다. 전송 보류는 **재시도** 또는 **전송 취소**로 해결한다. 회수·취소·만료가 확인되어 대기가 없어지면 다시 보낼 수 있다. 조회·앱 재시작만으로 자동 전송하지 않는다.

모바일 게시 영역은 댓글 정보와 같은 중앙 제목·양옆 구분선을 사용한다. 상태 확인 버튼은 제목 아래 오른쪽에 두며, 회수·취소 및 게시 대기 이력은 상태 구분 없이 전송 요청 생성 시각이 최신인 항목부터 표시한다.

확인 필요 계정도 게시본 준비 대상이다. 이것은 토큰이나 앱 연결이 검증됐다는 뜻이 아니다. 2026-10-28부터 토큰 확인은 PC 계정 관리에서 하며 휴대폰은 확인된 계정으로만 게시한다. 기존 PC 게시 이력은 별도로 보존하며 PC 원글·댓글·통계는 실행하지 않는다.

## 원문·실패·삭제 보호

- 전송은 고정 requestId, 대상 계정과 계정 버전, 원문 libraryId/postKey/draftCreatedAt/revision, 댓글 수정 시각, 최종 파일 SHA-256으로 식별한다. Python 원문의 미세초가 있는 시각 문자열을 임의 정규화하지 않는다.
- 전송 의도를 먼저 사용자·서비스별 OS 암호화 파일에 저장한다. 서명 URL·AWS 키·서비스 Bearer를 renderer나 전송 manifest에 넣지 않는다.
- 응답 유실은 같은 ID로 조회한다. 명시적 재시도 전에 서버의 저장 사본과 전체 manifest를 비교하고 최신 로컬 원문·파일도 다시 확인한다. 이미 취소·만료·시작·게시한 사본을 새 전송 성공으로 표시하지 않는다.
- 전송 중 원문 변경·삭제·복원·앱 종료·업데이트 재시작을 차단한다. 인증이 중지되거나 서비스 연결 실패가 확인되면 기존 실행권과 진행 중 PUT을 중단하고 원문·암호화 보류는 보존한다.
- 미회수 uploading/ready가 있으면 본문·미디어 편집을 차단한다. 시작·게시된 사본의 본문·미디어는 불변 이력으로 보존하고 로컬 새 revision 편집과 구분한다. 댓글은 아래 2026-10-20 항목을 따른다.
- 등록 글 삭제 확인창은 모바일 게시 대기 취소도 안내한다. 확인 취소 시 서버 작업은 없으며, 승인 후 서버 취소 영수증을 확보한 뒤에만 로컬 삭제를 실행한다. 원글 시작·완료·결과 불명 및 그 댓글은 보존한다. 중앙 취소 실패 시 로컬 삭제하지 않는다.
- 앱이 생성한 marker와 UUID가 있는 `mobile-outbox` 준비 복사본만 재시작·재시도 시 정리한다. 외부 원본·라이브러리 미디어·암호화 전송 기록은 이 정리 대상이 아니다.

## 서버·S3 계약

서버는 독립 `threads-admin-api`의 `/api/v1/publications`를 사용한다. 직원 desktop 세션과 소유권을 매번 검사하고 관리자·다른 직원·mobile 세션에는 이 API의 본문·미디어·서명 URL을 제공하지 않는다. 모바일 조회는 후속 별도 계약이다.

처음에는 단일 PUT으로 첨부 1~20개, JPEG/PNG 각 8MiB 이하, MP4/MOV 각 1GiB 이하를 지원한다. WebP는 PNG로 변환해 보내며 체크섬은 변환된 PNG 바이트에서 계산한다. 2026-10-20부터 변환은 앱에 포함된 Python Pillow 작업 파일 `local-runtime/convert_upload_image.py`가 맡는다. 이전에는 Electron `nativeImage`로 변환했는데, `nativeImage`는 PNG·JPEG만 읽기 때문에 WebP 첨부 전송이 항상 실패했다(0.1.7에서 수정). 변환에 실패하면 포괄 오류 대신 구체적인 이미지 오류를 보여 준다. multipart 부분 재개는 없고 명시적 재시도에서 파일 단위로 보낸다.

기존 버킷에서 `threads/dev/`와 `threads/prod/`를 분리한다. 임시 `staging/`에 Content-Type·Content-Length·SHA-256·If-None-Match를 고정한 서명 PUT을 발급하고, 서버는 HEAD 검증 후 S3 내부 복사로 `published/`에 확정한다. 완료 시도마다 새 final key를 만들고 필요한 경우 version ID로 고정해 늦은 완료가 수락된 파일을 덮어쓰지 못하게 한다. 파일 바이트는 서버를 거치지 않는다.

서명 URL은 main에서만 사용하며 HTTPS AWS S3의 허용 주소·정확한 헤더·파일 체크섬을 검사한다. 서비스 Bearer를 S3에 보내지 않고 redirect를 따르지 않는다. PUT의 412 응답은 이전 전송 가능성만 의미하며 최종 HEAD 비교로 판정한다.

전송 완료 시각+7일과 S3 Lifecycle 삭제 시점은 별개다. 운영 환경에서 실제 파일 존속·권한·정책을 확인해야 하며 Expiration 헤더가 없다는 이유로 보관을 보장하지 않는다. [S3 설정 안내](s3-publication-setup.md)를 사용자가 적용한다.

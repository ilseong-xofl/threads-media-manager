# 개발/운영 분리 설계 (2026-11-20)

상태: **구현 완료, `main`에 합침(2026-11-20, `a621d2e`).** 로컬 검사(TypeScript 1,658개, Python 617개, lint·typecheck·형식)와 CI(macOS, Windows 개발용, Windows 운영용)가 통과했다. CI의 실행 화면에서 개발용은 "(개발) ILS 소셜(T) 관리" 로그인 화면, 운영용은 "ILS 소셜(T) 관리"와 "서비스에 연결할 수 없습니다"(운영 서버가 아직 없다)로 떴다. 아직 릴리스는 내지 않았고 운영 저장소도 만들지 않았다. 설치와 자동 업데이트는 Windows PC에서 확인해야 한다(8장). 아래는 설계 경위다. 설계 확정 뒤 처음 설계안을 두 리뷰어(Claude 새 눈, Codex)가 검토했고(2026-11-20), 그 결과를 보고 사용자가 구조를 다시 정했다. 이 문서는 다시 정한 구조다. 사용자가 정하지 않은 부분은 맨 아래 "Claude가 판단한 것"에 모았다.

## 1. 목표

개발 한 벌과 운영 한 벌을 따로 두고 둘 다 계속 쓴다. 테스터는 운영 개시 뒤에도 개발 한 벌(PC 프로그램·휴대폰 앱·모바일 웹·관리자 웹/API·DB)로 새 작업을 시험하고, 직원은 운영 한 벌만 쓴다.

사용자 결정:

1. 지금 테스터 PC에 깔린 프로그램은 **개발용**으로 이어 간다(설치 위치·자료 폴더·자동 업데이트 그대로).
2. 운영용 PC 프로그램 이름은 **"ILS 소셜(T) 관리"**, 개발용에는 **"(개발)"** 표시를 붙인다.
3. **운영용 릴리스는 별도 저장소 `ilseong-xofl/threads-media-manager-prod`에 올린다**(개발 저장소 이름 뒤에 `-prod` — 사용자 결정). 개발용은 지금 저장소의 릴리스를, 운영용은 새 저장소의 릴리스를 따라 **둘 다 자동 업데이트**한다. 두 프로그램의 업데이트가 서로 만나지 않는다.
4. 작업 폴더를 다른 벌이 열지 못하게 막는 기능은 넣지 않는다. 규칙으로만 둔다(4장).
5. 순서: PC 프로그램 분리 → Play 내부 테스트 등록.

처음 안(저장소 하나에 개발용은 사전 릴리스, 운영용은 정식 릴리스)을 버린 이유: 업데이트 서비스는 어느 프로그램의 업데이트인지 보지 않고 그 저장소의 최신 정식 릴리스를 그대로 준다. 저장소를 같이 쓰면 예전 설치 파일을 다시 실행한 PC가 운영용 패키지를 받고, 개발용 릴리스가 실수로 정식으로 풀리면 전 직원 PC가 개발용을 받는다. 저장소를 나누면 이 경로가 없다.

## 3. PC 프로그램: 같은 소스에서 두 벌

설치용 빌드를 만들 때 `TMM_VARIANT=dev|prod`로 고른다. 벌마다 다른 값은 저장소의 파일 하나(`variants.json`)에 모으고, 빌드 설정·프로그램·검증 스크립트·CI가 모두 그 파일을 읽는다. 비밀값은 없다.

| 항목 | 개발용 (`dev`) | 운영용 (`prod`) |
| --- | --- | --- |
| 화면에 보이는 이름(창 제목·로그인 화면·머리글) | (개발) ILS 소셜(T) 관리 | ILS 소셜(T) 관리 |
| 실행 파일 | `ThreadsMediaManager.exe` (그대로) | `IlsSocialManager.exe` |
| 설치 식별자(Squirrel `name`) | `threads_media_manager` (그대로) | `ils_social_manager` |
| 설치 파일 | `ThreadsMediaManager-win32-x64-Setup.exe` (그대로) | `IlsSocialManager-win32-x64-Setup.exe` |
| 시작 메뉴·바탕 화면 바로가기·프로그램 목록 이름 | (개발) ILS 소셜(T) 관리 (0.1.11까지 Threads Media Manager) | ILS 소셜(T) 관리 |
| 시작 메뉴 폴더·게시자 | ILS 소셜(T) 관리 (0.1.11까지 Threads Media Manager) | ILS 소셜(T) 관리 |
| 아이콘 | 주황 배지(`app-icon-dev`) | 파란 배지(`app-icon`) |
| AppUserModelId | `com.squirrel.threads_media_manager.ThreadsMediaManager` (그대로) | `com.squirrel.ils_social_manager.IlsSocialManager` |
| 자료 폴더(`%APPDATA%`) | `ThreadsMediaManager` (그대로) | `IlsSocialManager` |
| 접속 서버 | `https://threads-admin-dev.ilscp.net` | `https://threads-admin.ilscp.net` |
| 자동 업데이트가 보는 저장소 | `ilseong-xofl/threads-media-manager` (그대로) | `ilseong-xofl/threads-media-manager-prod` (새 저장소) |

- **개발용은 눈에 보이는 것만 바꾼다.** 설치 쪽 식별(실행 파일 이름, 설치 식별자, 설치 파일, AppUserModelId, 자료 폴더, 접속 서버, 업데이트 저장소)은 하나도 건드리지 않는다. 지금 설치본이 자동 업데이트로 그대로 넘어와야 하기 때문이다. 0.1.11에서는 화면 안의 이름만 바꿔 시작 메뉴에 "Threads Media Manager"로 남았다. 사용자 결정(2026-11-20)으로 그다음 버전부터 바로가기·프로그램 목록 이름(실행 파일의 제품 이름)도 "(개발) ILS 소셜(T) 관리"로 맞추고, 시작 메뉴 폴더(회사 이름)는 운영용과 같은 "ILS 소셜(T) 관리"로 두며, 아이콘 배지를 주황으로 구분한다. 예전 이름의 바로가기는 업데이트 직후 프로그램이 지운다. 앱 이름(`app.setName`)은 "Threads Media Manager" 그대로다(포장하지 않은 Mac 실행의 키체인 항목 이름). 상세는 [Release 계약](windows-release.md)의 두 벌 절.
- **운영용의 한글 이름은 표시용으로만 쓴다.** 폴더·파일 이름에 들어가는 값(포장 도구의 `name`, 실행 파일, 설치 식별자)은 영문으로 두고, 한글 이름은 실행 파일 정보(`win32metadata`의 제품 이름·설명·회사 이름)와 설치 패키지 제목에 넣는다. 개발용의 옛 이름("Threads Media Manager")이 운영용의 회사 이름·게시자에 새지 않게 한다.
- **접속 서버**는 설치용 빌드에서 `variants.json`의 값을 쓴다. 저장소 변수 `THREADS_ADMIN_API_URL`은 쓰지 않는다. 검증은 "주소가 들어 있다"가 아니라 "그 벌의 주소와 정확히 같다"를 본다.
- **업데이트 저장소**도 `variants.json`에서 온다(지금은 CI가 주는 `GITHUB_REPOSITORY`). 검증은 번들에 그 벌의 저장소 이름이 있고 **다른 벌의 저장소 이름이 없는지**를 본다.
- **포장하지 않은 로컬 실행(`pnpm start`)은 지금과 똑같다.** 접속 서버 기본값은 `http://127.0.0.1:4191`, 자료 폴더는 `TMM_USER_DATA`로 격리, 자동 업데이트 없음. 벌 설정은 설치용 빌드에만 적용한다. 화면 이름은 개발용 것을 쓴다.
- 패키지 이름(`package.json`의 `name`), 백업 파일의 앱 이름, 프로토콜 이름은 두 벌이 같다. 운영체제에 등록되는 것이 아니라 충돌하지 않는다.

## 4. 같은 PC에 둘 다 설치했을 때

- 설치 위치·자료 폴더·로그인·ChatGPT 연결·중복 실행 잠금은 서로 독립이다. 서버에 딸린 자료(계정, 로그인, 휴대폰으로 보낸 기록, 일상 글, 초안)는 각자의 자료 폴더에 있어 섞이지 않는다.
- ChatGPT 로그인 창은 두 벌이 같은 로컬 포트를 써서 동시에 열 수 없다. 그대로 둔다.
- **작업 폴더(수집 자료와 그 DB)**: 두 벌이 같은 폴더를 열어도 막지 않는다(사용자 결정). 같은 폴더를 쓰면 수집한 글과 초안이 두 벌에 똑같이 보인다. 알아 둘 점은 두 가지다.
  - 작업 폴더의 DB는 프로그램 버전이 정한 형식과 **정확히 같아야** 열린다(`local-runtime`의 `SCHEMA_VERSION` 검사). 개발용이 새 버전으로 형식을 바꾸면, 아직 그 버전이 아닌 운영용은 그 폴더를 열지 못한다.
  - 두 프로그램을 동시에 켜고 같은 폴더를 쓰면 안 된다.
  - 그래서 두 벌을 같이 쓰는 사람(사용자·테스터)은 **벌마다 작업 폴더를 따로 쓰는 것을 규칙으로** 한다. 운영용만 쓰는 직원에게는 해당이 없다.
- 수집 도구(Codex 플러그인)는 PC마다 기본 작업 폴더 하나만 기억한다. 두 벌을 같이 쓰는 사람은 수집할 때 대상 폴더(`accounts.xlsx` 경로)를 지정한다.

## 5. 버전과 릴리스

버전 번호는 한 줄(`X.Y.Z`)을 두 벌이 같이 쓴다.

```
커밋 C (package.json 0.1.12)
 ├─ 이 저장소 CI: 개발용·운영용을 각각 빌드·검증 (push마다)
 ├─ 태그 v0.1.12 push → 이 저장소에 개발용 정식 릴리스 (지금 절차 그대로)
 │                      → 개발용 설치본이 자동 업데이트, 테스터가 확인
 └─ 운영 저장소에서 "릴리스 실행"(버전 0.1.12 입력, 사람이 직접 누름)
                        → 이 저장소의 태그 v0.1.12를 받아 운영용으로 빌드·검증
                        → 운영 저장소에 정식 릴리스 → 운영용 설치본이 자동 업데이트
```

- **개발용 릴리스는 지금과 같다.** 태그 `vX.Y.Z` → 이 저장소의 정식 릴리스. 바뀌는 것은 후보 이름에 벌이 붙는 것과 벌 검사가 추가되는 것뿐이다.
- **운영용 릴리스는 운영 저장소(`ilseong-xofl/threads-media-manager-prod`)의 작업이 한다.** 그 저장소에는 릴리스 작업 파일과 릴리스만 둔다. 소스는 이 저장소에 있다.
  - 사람이 버전을 넣고 직접 실행한다(태그만으로 나가지 않는다). 테스터 확인이 끝났다는 판단은 실행하는 사람이 한다.
  - 실행 조건: 이 저장소에 그 버전의 태그와 **공개된 개발용 릴리스**가 있어야 한다. 버전은 운영 저장소의 지금까지 릴리스보다 커야 한다.
  - 이 저장소의 태그를 받아 `TMM_VARIANT=prod`로 빌드하고, 이 저장소의 검증 스크립트를 그대로 돌린 뒤 운영 저장소에 릴리스를 만든다. 다른 저장소에 쓸 권한(토큰)이 필요 없다.
  - 운영용은 개발용과 다른 빌드다(서버 주소·이름·업데이트 저장소가 다르다). 그래서 같은 파일을 승격하는 것이 아니라 같은 커밋을 운영용으로 빌드한다.
  - 운영 버그를 급히 고칠 때도 같은 길이다: 고친 커밋에 버전을 올려 개발용으로 먼저 내고, 운영 저장소에서 그 버전을 실행한다.
- 업데이트 서비스는 공개 저장소만 쓸 수 있다. 운영 저장소는 공개여야 하고, 설치 파일과 릴리스 작업 파일만 들어 있다.
- 내려받기 링크
  - 개발용: `https://github.com/ilseong-xofl/threads-media-manager/releases/latest/download/ThreadsMediaManager-win32-x64-Setup.exe` (지금과 같다)
  - 운영용: `https://github.com/ilseong-xofl/threads-media-manager-prod/releases/latest/download/IlsSocialManager-win32-x64-Setup.exe`

### 운영용 첫 릴리스 전 예행 (운영 개시 때)

운영용에만 있는 것(새 설치 식별자, 새 자료 폴더, 운영 저장소 업데이트)은 개발용 시험으로 확인되지 않는다. 그래서 직원에게 링크를 주기 전에 사용자 PC에서 먼저 끝까지 본다.

1. 운영 저장소에 첫 릴리스를 낸다(링크는 아직 아무에게도 주지 않는다).
2. 사용자 PC에 설치한다: 시작 메뉴 이름, 개발용과 나란히 설치, 운영 서버 로그인.
3. 버전을 올린 두 번째 릴리스를 내고 자동 업데이트가 오는지 본다.
4. 이상이 없으면 직원에게 링크를 준다. 식별 이름을 바꿔야 하면 이 단계에서 바꾼다(직원 설치 전이라 바꿀 수 있다).

## 6. 바꿀 곳

- 벌 설정: 새 `variants.json`, `forge.config.ts`(실행 파일·설치 식별자·설치 파일·제목·`win32metadata`. 아이콘 주소는 두 벌 모두 이 저장소의 태그 주소를 쓴다 — 아이콘 파일이 여기에만 있다), `webpack.main.config.ts`와 렌더러 설정(벌·이름·서버 주소·업데이트 저장소 주입).
- 프로그램: `src/main/index.ts`(이름, AppUserModelId, 자료 폴더, 창 제목, 오류 창 제목, DB 백업 창의 이름), `src/renderer`(`App.tsx` 머리글·바닥글, `AuthenticationGate.tsx`, `index.html`). `src/main/updates.ts`는 그대로다.
- 검증: `scripts/verify-windows-package.mjs`, `scripts/verify-windows-release.py`, `scripts/verify-windows-ui.mjs`의 고정 이름을 벌 설정에서 읽게 하고, 서버 주소 일치·업데이트 저장소 일치(다른 벌의 값 없음)·설치 파일과 패키지가 같은 벌인지 검사.
- CI: `.github/workflows/ci.yml`에서 Windows 빌드를 벌별로 나란히(같은 작업 안에서 두 번 빌드하면 산출 경로가 겹치고 시간 제한을 넘는다). 후보 이름에 벌을 넣는다. `release-windows.yml`은 개발용 후보를 쓰도록.
- 운영 저장소의 릴리스 작업 파일: 이 저장소에 원본을 두고(`distribution/prod-release/`) 운영 저장소에 복사해 쓴다.

## 7. 운영 개시 때 할 일 (이 구현 범위 밖)

1. 운영 DB(`threads_admin_prod`) 만들기, migration 전부 적용, 관리자 계정 만들기. 개발에서 쓰던 직원의 로그인·Threads 계정·토큰은 `threads-admin-api`의 `pnpm accounts:copy`로 옮긴다(2026-11-23 사용자 결정 — 그 밖의 자료는 옮기지 않는다. 인수인계 문서의 "운영 준비"). 운영 서버가 정말 운영 DB에 붙어 있는지(개발 DB가 아닌지), 운영 S3 권한이 `threads/prod/`에만 닿는지 확인.
2. 관리자/API와 모바일 웹의 운영 이미지 빌드·배포(운영 도메인, `MOBILE_ORIGINS`).
3. 운영 저장소 만들기(공개), 릴리스 작업 파일 넣기, 5장의 예행.
4. 휴대폰 앱 운영용을 Play에 등록.
5. 가이드의 설치 링크와 이름 바꾸기.

운영 규칙: **개발 환경에서 올린 글도 실제 Threads 계정에 올라간다.** DB는 나뉘어도 Meta 쪽 계정은 하나다. 개발 환경에는 시험용 계정만 연결하고, 같은 Threads 계정을 개발과 운영에 함께 연결하지 않기를 권장한다(서버가 막아 주지 못한다. 2026-11-23 사용자 결정으로 필수가 아닌 권장 사항이고 가이드로 안내한다).

## 10. 구현 결과 (2026-11-20)

- 구현은 Claude 헬퍼가 별도 작업 폴더에서 했고, 리더가 핵심을 직접 확인한 뒤 Codex가 변경 전체를 검토했다.
- 벌 값은 `variants.json`, 읽는 코드는 `scripts/variants.mjs` 한 곳이다. 프로그램 코드는 이 파일을 읽지 않고 webpack이 고른 벌의 값만 상수로 넣는다. 그래서 번들에 다른 벌의 값이 들어가지 않는다.
- `TMM_VARIANT`가 없거나 틀리면 설치용 빌드가 실패한다. 기본 벌은 없다. 포장하지 않은 실행은 이 변수를 보지 않는다.
- 개발용이 지금과 같다는 확인: 값은 `src/shared/variants.test.ts`가 고정한다. 새 설정으로 만든 개발용 실행 파일이 이전 설정으로 만든 것과 바이트까지 같았고, 공개된 0.1.10 릴리스 파일이 새 검증을 개발용으로 통과하고 운영용으로는 거절됐다.
- 설계에 없던 것: `variants.json`에 `productName`·`companyName`·`packageName` 추가, 운영 릴리스는 벌 표시(`variant: dev`)가 있는 개발용 릴리스만 받는다(그래서 0.1.10 이하는 운영용으로 낼 수 없다).
- Codex 검토 8건 가운데 반영한 것: 운영 릴리스가 공개 단계에서 실패해 초안만 남았을 때 다시 실행할 수 있게, 배포되는 실행 파일의 제품 이름이 그 벌의 것인지 검사, 화면 검사가 "프로그램이 그 벌의 자료 폴더를 실제로 썼고 다른 벌의 폴더는 만들지 않았다"까지 확인, 벌 값이 프로그램의 어느 상수로 들어가는지 고정하는 테스트(서버 주소와 업데이트 저장소가 뒤바뀌는 경우), 로컬 실행이 틀린 `TMM_VARIANT`에도 멈추지 않게, 재현 명령 문서.
- 반영하지 않은 것: 설치 파일(Setup.exe)이 같은 패키지를 담고 있는지는 **이름으로만** 확인한다. 설치 파일과 패키지는 한 번의 빌드에서 함께 나오고 릴리스 때 체크섬을 다시 확인하므로, 더 깊은 확인(설치 파일 형식을 풀어 비교)은 넣지 않았다. 같은 폴더에서 벌을 바꿔 다시 빌드하려면 `out/`을 먼저 지워야 한다(문서에 적음).

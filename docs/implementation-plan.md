# 작은 단위의 구현과 검증

**2026-09-22 최신 결정:** 사용자 중지 없는 다운로드, 비정상 종료 후 복구·재개, 동일 라이브러리 재연결과 DB 백업·복원을 구현한다. [다운로드 복구 계획](download-completion-plan.md)과 [DB 관리](database-maintenance.md)를 적용하고 [통합 검증](download-recovery-verification.md)을 마친 뒤 API 관련 작업, Windows 배포 순서로 진행한다. 영상 비율 크롭은 기능 목록에서 제외한다. 이전 계획 정리·전체 보류 안내보다 이 결정이 우선한다.

1A–1D와 1E 정상 다운로드·복구·재개, 1F 주요 목록·상세·관리·재연결·DB 백업·복원을 구현했다. 1G Windows 검증·배포는 미완료다. 아래 표는 원래 단계별 목표·완료 기준이며 모든 항목의 통과 기록이 아니다.

플러그인은 수집 전용이고 앱이 다운로드·자료 관리를 소유한다. 단일 파일 파일럿에서 시작해 [1D](phase-1d-download.md)와 [1E](phase-1e-download.md)로 확장했다. 다운로드 일일 횟수 제한은 없으며 기존 이력·대기·중단을 보존한다. 사용자 요청으로 이미지 중심 그리드·상세 캐러셀, 편집·삭제·댓글 정보·ZIP까지 구현했다. 과거 검증은 [진행 기록](progress.md)과 기능별 문서의 해당 시점 기록으로 읽는다.

## 현재 구현: 다운로드 복구·DB 관리 / 이후: API

사용자가 Phase 2를 시작했다. 한 원글 안에서 원본·편집본을 선택하고 순서를 조정한 뒤 캡션과 함께 SQLite에 등록한다. 원글당 한 개를 계속 수정하며 실제 API 게시는 Phase 3이다. [등록 기능 계약](phase-2-registration.md)을 따른다. 로컬 등록과 다운로드 복구·재연결·DB 관리 기능을 구현했다. API 관련 작업과 Windows 배포는 이후 단계다.

## Phase 1 순서

재개 시 적용할 개발·플랫폼 검증 기준은 다음과 같다. 현재는 아래 기준에 따라 다음 단계를 자동 시작하지 않는다.

- **1A–1F:** Mac에서 개발하고 단위·기능·통합 테스트를 수행한다. 각 단계의 Mac 완료 기준을 통과하면 다음 단계로 진행한다.
- **기능 지원:** 수집 플러그인·앱 로컬 실행기·Electron은 Mac과 Windows에서 동작하도록 구현한다. 경로·프로세스·파일 잠금·권한·런타임 차이를 처리하고 사용자별 절대 경로나 특정 OS 명령을 공통 코드에 고정하지 않는다.
- **Mac:** 개발 환경 직접 실행용이다. Mac 설치 파일·자동 업데이트 배포는 만들지 않는다.
- **1G:** Mac에서 구현·통합 검증을 마친 후 Windows로 옮겨 전체 기능, 의존성, 경로·잠금, 설치 파일, 업데이트와 데이터 보존을 최종 검증한다. 설치 파일과 앱 자동 업데이트는 Windows만 배포한다.
- Windows 미검증은 1G 잔여 항목으로 관리한다. **개발 단계 완료와 Windows 배포 준비 완료는 별도 판단**이다. Mac 다운로드 복구·DB 관리의 검증 범위는 최신 통합 검증 기록을 따른다.

초기 1A–1C는 실제 CDN 다운로드 없이 검증했고, 이후 1D·1E에서 앱 다운로드로 확장했다. 과거의 “다음 구현은 Electron 기반과 원본 읽기” 안내는 완료된 초기 순서다. 파일럿의 검증만으로 이후 단계나 Windows 완료를 선언하지 않는다. 읽기·다운로드의 Excel 원문 보존 원칙은 유지하며, 사용자가 확인한 게시글 삭제에 한해 삭제 여부·시각을 기록하는 현재 기능은 별도 예외다.

이전 소스 체크포인트에서 사용자가 GitHub 저장소 생성·업로드를 요청했다. 실제 생성·push 결과는 게시 작업 기록에서 확인한다. 소스 보관과 설치 파일·Release·업데이트 배포는 구분하며 후자는 최종 배포 단계로 둔다.

플러그인은 state.db·다운로드 중단 상태를 읽거나 쓰지 않는다. 앱의 로컬 실행기가 상태와 미디어를 소유한다. 활성 수집과 다운로드는 공통 `_work/collector.lock`으로 겹치지 않게 하며 단순 앱 열기·화면 조회는 잠금을 독점하지 않는다. 앱 오류로 나중에 별도 요청한 수집을 자동 금지하지 않고, 새 Excel로 앱 중단·소비·휴식을 초기화하지 않는다.

입력 fixtures와 HTTP 모의 응답에는 테스트용 식별자·주소를 사용한다. 실제 수집 Excel·서명 URL·미디어·개인 경로·DB를 공개 저장소에 넣지 않는다. 실제 자료 기반 수동 검증은 개인 경로에서 별도로 한다.

추가 근거와 운영 상한의 의미는 [CDN 다운로드 조사와 대응](cdn-download-guide.md)에 기록했다. 초기 실물 검증은 모의 검증 후 파일 1개·소량 순서로 시작했고, 이후 사용자가 요청한 전체 다운로드를 검증했다. 이 과거 절차는 현재 추가 전송 지시가 아니며 서비스 허용량이나 차단 회피 검증으로 표현하지 않는다.

계정별 회차·중단·복구는 [다운로드 대기열 정책](download-queue-policy.md), 개인 계정 설치·갱신은 [플러그인 배포](plugin-distribution.md)를 따른다. 게시글 단위 완료·첫 다운로드 오류에 앱 다운로드 전체 중단은 고정 요구사항이며, 예시 수치를 영구 상수로 테스트하지 않는다. 목표 범위·간격·redirect 등의 운영값은 서로 일관된 정책으로 설정한다. 계획 계산은 모의 입력과 가상 시계로 먼저 검증하고 실제 CDN 요청량을 늘려 한계를 시험하지 않는다.

## Phase 1 완료 판단

1A–1F는 해당 단위의 Mac 검증 결과로 개발 완료를 판단한다. 이후 1G의 Windows 실제 기능·설치·업데이트 검증까지 통과해야 Phase 1 배포 준비 완료다. Mac 개발 성공만으로 Windows 검증을 통과 처리하지 않는다. 샘플 URL이 오래되어 접근 실패하면 다운로드 기능 결함과 원본 후보 사용 불가를 구분하고, 엑셀의 만료 추정만으로 서버 결과를 추정하지 않는다.

배포 전에 새 저장소의 공개 범위와 실제 update 대상, Windows 검증 환경, 최초 앱 버전을 정한다. Windows 코드 서명은 기반 앱의 준비 상태를 1G에서 다시 확인하고, 검수용 후보 및 실제 배포에 서명을 적용할지 구분해 결정한다. 인증서가 준비되어 있다고 가정하지 않는다. 과거 Excel 어댑터는 Python 표준 zipfile/ElementTree를 사용한다. 파일럿 이미지는 제공 런타임의 Pillow 12.3으로 검증하고 영상은 PATH의 ffprobe가 없으면 HTTP 전에 중단한다. Windows 의존성 준비·실제 기능 검증은 1G에서 확인한다.

초기 전환 기록의 **HTTP 1회/24시간 파일럿**, “Electron·전체 다운로드·35–45첨부 회차는 후속”이라는 문구는 현재 상태를 설명하지 않는다. 사용자 요청으로 일일 횟수 상한을 제거했고 정상 회차 다운로드를 구현했다. 현재는 사용자 중지를 제거하고 비정상 종료·오류 후 명시적 재개를 제공한다. 90회 정책이나 과거 임시 배치 초안을 현재 정책으로 적용하지 않는다. 기존 단독 스킬을 덮어쓰지 않고 [진행 기록](progress.md)의 미확인 항목을 완료로 바꾸지 않는다.

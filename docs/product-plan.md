# 제품 범위와 단계

상태: 2026-09-22 최신 결정은 **다운로드 복구·DB 관리 → API 관련 작업 → Windows 배포** 순서다. 사용자 중지는 제공하지 않고 비정상 종료 후 명시적 이어서 다운로드, 기존 대상의 원본 재검증, 동일 라이브러리 재연결, DB 백업·복원을 구현했다. [다운로드 계약](phase-1e-download.md), [DB 관리](database-maintenance.md), [검증 기록](download-recovery-verification.md)을 따른다. API 게시와 Windows 배포는 미완료다. 이전 체크포인트는 당시 기록으로 읽는다.

아래 단계표는 2026-09-21 설계 목표를 보존한 것이며 전체 완료 목록이 아니다. 공개 저장소에 소스를 보관하고 향후 Windows 자동 업데이트를 제공하기로 했으며, 실제 생성·push 성공은 실행 결과로 확인한다. 소스 보관이 설치 파일·Release·Windows 준비 완료를 뜻하지 않는다. 아래 기반 버전은 당시 읽기 확인이다.

## 1. 제품 기준

사내 멤버가 모두 개인 Codex 계정으로 플러그인을 설치하고 각자의 로그인된 내부 브라우저로 원하는 Threads 계정을 수집한다. 플러그인은 수집 결과를 저장하고 종료한다. Threads Media Manager 앱은 저장된 결과를 읽어 다운로드하고 관리한다. 사용자 간 동기화·공유 로그인·중앙 DB·회사 워크스페이스 배포에 의존하지 않는다.

플러그인은 `계정 A 수집 → 결과 Excel 확정 → 계정 기준 표시 → 수집 계정 간 휴식 → 계정 B 수집`을 진행한다. 앱은 별도의 사용자 요청으로 검증된 Excel을 읽고 다운로드 계획을 만든다. 각 계정 안에서 남은 첨부 35–45개에 들어오는 게시글 묶음으로 회차를 나누고 마지막 잔여분은 하한 미만이어도 처리한다. 정상 회차 다운로드와 비정상 종료·오류 후 명시적 재개를 구현했다. 사용자 중지 버튼과 다운로드 중 일반 앱 종료는 제공하지 않는다. 앱의 로컬 실행기 한 곳만 다운로드·상태 DB·미디어 파일을 갱신한다. 플러그인은 다운로드 명령이나 DB·중단 상태에 의존하지 않으며 앱에 수집 브라우저·세션 복사·페이지 API 조회를 추가하지 않는다.

설치·버전 관리는 [개인 계정 플러그인 배포](plugin-distribution.md)를 따른다. 초기에는 검증된 단일 파일 파일럿을 플러그인 밖 `local-runtime/`으로 옮겼으며, 당시 코드 이동만으로 앱·배치 완료를 뜻하지 않았다. 이후 앱 통합과 정상 회차 다운로드를 구현했다. 현재 범위는 [1E 다운로드](phase-1e-download.md), 초기 계약은 [로컬 다운로드 실행기](local-download-runner.md)를 참고한다. 초기 24시간 1회 상한은 사용자 요청으로 제거했고 일일 횟수 제한은 없다. 90회 정책이나 과거 미완성 배치 초안을 현재 정책으로 적용하지 않는다.

현재 수집 계약은 요청마다 계정당 새 미디어 원글 최대 2건이 기본이며, 사용자가 이번 요청에 다른 건수를 지정할 수 있다. 하루 횟수 제한은 없고, 이전 기준 ID를 먼저 만나면 해당 계정은 0~목표 건수만 수집한다. 목표 건수에서도 기준 ID를 못 찾으면 누락 가능성을 기록하고 새 첫 ID를 다음 기준으로 삼는다. 앱은 이 기준이나 accounts.xlsx를 변경하지 않는다.

## 2. 단계별 범위

| 단계                    | 만드는 기능                                                                                                       | 완료 기준                                                                                                                                                                                        |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Phase 1: 수집 자료 보기 | 수집 전용 플러그인 설치·갱신, Electron 기반·Excel 읽기, 앱의 다운로드 실행기·상태 DB·로컬 자료 표시, Windows 배포 | 개인 Windows 환경에서 설치·갱신과 데이터 보존 검증. 정상 다운로드는 선택한 게시글 첨부 전부 완료, 첫 오류는 앱 다운로드 전체 중단·미완료. 별도 수집 실행과 중단 상태 분리, 중복·게시글 분할 없음 |
| Phase 2: 게시글 준비    | 한 원글의 원본·편집본 선택, 순서 변경, 캡션 작성·Codex 생성, 게시글 등록·조회·수정                                | 원글당 한 개를 SQLite에 등록하고 수정. 원문·파일을 보존하며 선택한 미디어 ID·순서와 캡션을 저장                                                                                                  |
| Phase 3: API 게시       | Threads 계정 연결, 이미지·영상·혼합 캐러셀 게시, 미디어 전달, 게시 목록과 실패 복구                               | 실제 원격 게시 ID 및 게시 당시 캡션·첨부 이력 보존. 결과 불명 요청의 무조건 재게시 방지                                                                                                          |
| Phase 4: 사전 답글      | 게시물마다 이미지 한 장+캡션 답글 준비, 필요 시 전송, 전송 이력                                                   | 대상 게시 ID와 답글 ID 연결, 중복 전송 방지                                                                                                                                                      |
| Phase 5: 간단 편집      | 이미지 크롭, 영상 프레임 캡처, 영상 구간 자르기                                                                   | 원본 보존, 파생 파일과 원본 연결                                                                                                                                                                 |

초기 계획은 Phase 1에서 캡션 수정·AI 생성·게시 예약·API 연결·답글·편집기를 제외했다. 이후 사용자 요청으로 **게시글별 로컬 댓글 캡션·링크 등록**, **이미지 크롭·영상 프레임 캡처·영상 구간 자르기**를 앞당겨 구현했다. 새 게시글 준비는 Phase 2에서 구현하며, 원문 수정·실제 답글 전송·API 게시는 제공하지 않는다. 원본·편집본 ZIP, 확인 후 삭제와 Excel 삭제 표시, 외부 링크 열기, 페이지·날짜 필터도 현재 제공한다. [편집](media-editing.md), [댓글](post-comments.md), [삭제](media-deletion.md)를 따른다.

영상 비율 크롭은 사용자 결정으로 기능 목록에서 제외했다. 기존 이미지 크롭·영상 캡처·영상 구간 자르기는 유지한다. 계정 연결, 게시글·답글 전송, 미디어 전달, 전송 이력·실패 복구 등 API 관련 작업은 다운로드 잔여 완료 후 함께 진행한다. Phase 4 답글 이미지 처리 요구도 이때 함께 정리한다.

Phase 4의 요청 감지는 아직 정해지지 않았다. 첫 설계는 사용자가 확인하고 답글을 전송하는 흐름이며, 자동 감지·자동 응답은 별도 결정 사항이다. 답글이 항상 맨 위에 표시되거나 고정된다고 전제하지 않는다.

Phase 1은 원문 정보를 DB에 복제하지 않고, 결과 Excel을 읽어 메모리에서 병합한 결과와 앱 실행기의 DB 작업 상태를 연결한다. 플러그인은 state.db를 읽거나 쓰지 않는다. DB 쓰기·migration은 앱의 로컬 실행기 한 경로로 제한한다. 활성 수집과 다운로드는 수집 루트의 공통 실행 잠금으로 겹치지 않게 한다. 앱 다운로드 오류는 별도로 요청한 수집을 자동 금지하지 않으며, 새 Excel은 다운로드 중단 해제나 자동 재시작 조건이 아니다. 결과 Excel은 다운로드 성공 뒤에도 보관한다. 기존 daily-v1 Excel은 변환 없이 읽는다. 파일을 잃으면 로컬 미디어와 연결 키는 남지만 원문 캡션을 DB에서 복원할 수는 없다.

## 4. local-video-manager 재사용 기준

2026-09-21 읽기 확인 기준: `local-video-manager`의 `main`, `ddb046e`, 변경 파일 없음. 아래 버전은 확인 시점의 기반이며 새 구현 때 재확인한다.

| 항목          | 확인한 기반                                                                         |
| ------------- | ----------------------------------------------------------------------------------- |
| 개발          | Node 24.18.0, pnpm 10.28.1, hoisted node linker                                     |
| UI·언어       | React/React DOM 19.2.8, TypeScript 5.9.3                                            |
| 데스크톱·빌드 | Electron 43.3.0, Forge 7.11.2, Webpack 5.109.2                                      |
| DB·검증       | better-sqlite3 13.0.3, Vitest 4.1.10, 기존 lint/typecheck/format 체계               |
| Windows       | Squirrel, electron-squirrel-startup 1.0.1, update-electron-app 3.3.0, 공개 Releases |

가져오는 것은 Electron main/preload/renderer 분리, 제한된 IPC, 로컬 미디어 응답과 byte-range 처리, SQLite 관리 패턴, 개발·검증·Windows 앱 업데이트 구조다. 앱의 로컬 실행기는 별도 프로세스로 두며 SQLite 네이티브 의존성이 Electron과 같은 바이너리로 동작한다고 전제하지 않는다. 실행기용 런타임과 OS 차이는 Mac 개발 중 양쪽 지원을 고려해 구현하고, Windows 배포 적합성은 최종 1G에서 검증·확정한다. 기반 버전은 임의로 올리지 않는다. 과거 Excel 읽기는 Python 표준 라이브러리 어댑터를 사용하며 실제 양식 호환성을 별도로 확인한다.

기존 앱의 로그인 화면·Service API·세션 토큰·권한 재검사·서버 캡션 생성·사용량·서비스 URL 주입은 새 앱에서 제외한다. 편집기·프리셋·기존 라이브러리 DB와 migration·편집 전용 FFmpeg 구성도 복사하지 않았다. 이후 사용자 요청으로 새 앱 자체의 편집 기능과 PATH의 ffmpeg를 이용한 영상 구간 편집을 구현했다. 인증 제거와 별개로 IPC 입력 검증·파일 경계·창 격리는 유지한다.

새 앱은 새 package 이름, executable, Squirrel 이름, 앱 ID, preload 공개명, DB application_id, userData, cache, GitHub update 대상이 필요하다. 기존 사용자 DB·미디어·Release를 공유하지 않는다. 앱 식별자는 Electron 기반을 만드는 1C에서 한 파일의 상수로 확정하고 1G에서 패키지·바로가기와 대조한다.

저장소 대상은 공개 `ilseong-xofl/threads-media-manager`로 정했다. local-video-manager와 같이 소스와 향후 Releases를 같은 공개 저장소에서 관리한다. 이는 자동 업데이트에 소스 공개가 필수라는 뜻은 아니다. 이번에는 소스를 보관하며 실제 생성·push 결과는 실행 후 확인한다.

Windows 설치 앱은 local-video-manager에서 확인한 `ElectronPublicUpdateService` 방식을 따를 계획이다. 패키지 앱에서 1시간 간격으로 확인하고 백그라운드 다운로드 후 사용자가 나중에 적용하거나 지금 재시작하도록 안내한다. **현재 TMM updater 코드는 미구현**이며 설치 파일·업데이트 구현·Windows 실제 검증은 배포 단계에 남아 있다. 기존 앱의 Release·업데이트 대상을 공유하지 않는다.

## 5. 커뮤니티 프로젝트 활용

`ddalkkak-threads-community`는 Phase 1에서 코드를 가져오지 않는다. 당장 필요한 Excel 읽기·Threads 미디어 다운로드 기능이 그대로 준비되어 있지 않아 도입 이점이 적다.

Phase 3에서 미디어 전달과 게시 컨테이너 처리의 참고 대상으로 다시 평가한다. 이전 정적 검토의 기준 커밋은 `81978efb9ba6bfdcbf5e91932312b99f2810d3b1`이며 현재 동작 보증이 아니다. 직접 코드 도입 시 해당 시점 라이선스와 재사용 범위를 검토한다.

게시 단계에서는 Threads API의 당시 권한·형식·제한을 공식 문서로 재검증한다. 로컬 파일을 Meta가 가져갈 수 있는 전달 방법, 원격 결과 불명 상태, 게시 ID 저장 복구가 필요하다. 이번 설계에서 서버나 외부 저장소를 만들지는 않는다.

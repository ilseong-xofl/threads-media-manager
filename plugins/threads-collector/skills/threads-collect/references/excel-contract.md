# daily-v1 필드와 Excel 보고서 계약

필드 계약은 `daily-v1`이며 **결과 Excel이 유일한 최종 원본**이다. 수집 중 JSONL은 임시 복구 기록이고 저장·검증 후 정리한다. 로컬 앱은 Excel을 읽기 전용으로 사용하고 SQLite에는 작업 상태만 저장한다.

Excel 형식 버전은 `daily-v1`이다. `accounts.xlsx`는 `계정` 1개 시트, 날짜별 결과 Excel은 `게시글`·`미디어`·`실행기록` 3개 시트다. 모두 제목 2행, 안내 4행, 헤더 6행, 데이터 7행부터다. 각 시트의 `A3=형식 버전`, `B3=daily-v1`을 확인한다. 실제 입력에서는 열 이름으로 읽고 사용자 추가 열·메모·서식을 보존한다. 파일 배치/갱신/복구는 [storage-layout.md](storage-layout.md)를 따른다. 다운로드 실행기와 앱은 정상 흐름에서 결과 Excel을 읽고 계정 입력을 변경하지 않는다.

## 계정

| 열 | 의미 |
|---|---|
| 사용 | Y/TRUE/1만 활성 |
| 계정명, URL, 메모 | 사용자 입력. URL은 Threads 프로필 |
| 기준게시글ID | 최신 완료 Excel 기준 ID의 표시·복구용 사본. 다음 수집 기준은 영구 원본에서 읽음 |
| 최근 시도(KST) | 최근 계정의 실제 시도 시작 시각. 같은 날 재요청을 막는 값이 아니며 파일의 수집일자와 다를 수 있음 |
| 최근 완료(KST) | 마지막 완료 실행의 실제 종료 시각. partial에는 갱신하지 않음 |
| 최근 결과, 특이사항 | 최신 실행 요약. 이전 경고는 실행기록에 보존 |
| 최근실행ID | 계정 파일에 반영한 마지막 실행 ID. 저장 복구 중복 방지 |
| 최근결과파일 | 루트 기준 상대 경로, 예: results/2026/09/threads-2026-09-17.xlsx |

배포 계정 양식의 7행에는 입력 예제 `Y | sample | https://www.threads.com/@sample`이 있다. 사용자는 예제 계정을 삭제한 뒤 실제 계정을 등록한다. 활성 예제 계정은 브라우저 호출 전 전체 실행 중단 사유이며, 기존 파일을 연결하거나 초기 설정·업데이트를 반복할 때 예제를 자동 삽입하지 않는다.

기준은 바깥 원글 permalink의 코드로 일관되게 기록한다. ID는 숫자 변환이나 크기 비교를 하지 않는다. 계정명 표기가 바뀌었을 때 같은 계정인지 추정하여 이력을 합치지 않는다.

결과 Excel 기준이 비어 있고 완료 이력 없이 initial의 running/partial만 있으면 정상적인 최초 수집 중단 상태다. 최초 목록 끝에서 적격 글이 0건이고 다음기준ID가 비어 있는 end_reached도 정상 상태다. 두 경우 모두 다음 허용 실행에서 최신 상단부터 initial로 확인한다. 이 경우를 기준 분실로 건너뛰지 않는다. 이전 완료 Excel 실행에 실제 다음기준ID가 있었는데 계정 표시만 사라졌다면 그 기록으로 표시를 복원하고, 근거가 없으면 skipped_invalid로 남긴다.

## 게시글

키: `(계정명, 게시글ID)`.

| 열 | 의미 |
|---|---|
| 계정명, 게시글ID, 원문URL | 원글 식별자와 영구 링크. URL 갱신 시에도 보존 |
| 등록일(KST), 수집일(KST) | 확인한 절대 게시 시각, 이 날짜 파일에 처음 저장한 시각 |
| 최근확인시각(KST) | 이 행을 가장 최근에 실제 관찰한 시각. 단순 파일 저장 시각으로 바꾸지 않음 |
| 캡션 | 원문·줄바꿈 보존, 수식이 아닌 리터럴 텍스트 |
| 이미지 수, 영상 수 | 실제 확인된 첨부 수; 미확인 전체 수를 0으로 추정하지 않음 |
| 캡션 상태 | `complete`, `partial`, `unknown`; 캡션 없는 것이 확인되면 빈 값 + complete |
| 첨부 상태 | `complete`, `partial`, `unknown`; URL 해결 여부와 별개 |
| 확인실행ID | 이 행의 가장 최근 관찰을 기록한 실행 ID |

정확한 등록일이 없으면 빈 날짜와 실행 특이사항으로 남긴다. 같은 날짜 파일에서는 키로 갱신하고 수집일은 유지하며 실제 재관찰 시 최근확인시각/확인실행ID를 갱신한다. 이미 완전한 캡션·첨부를 더 불완전한 관찰로 덮어쓰지 않는다. 다른 날 재개해 같은 ID를 확인하면 오늘 파일에 오늘의 관찰을 저장할 수 있다. 전 기간 최초 수집 시각은 로컬 앱이 ID별 가장 이른 수집일로 관리한다.

## 미디어

키: `(계정명, 게시글ID, 순서)`. 캐러셀 순서를 확정할 수 없으면 임의 연결하지 않고 첨부 상태를 partial로 남긴다. 서명 URL이 달라져도 새 첨부로 세지 않는다.

| 열 | 의미 |
|---|---|
| 계정명, 게시글ID, 순서 | 원글과 첨부 순서, 순서는 1부터 |
| 종류 | `image` / `video` |
| 다운로드URL | 관찰한 HTTPS 파일 URL 후보, 쿼리 포함 전체 문자열. 없으면 빈 값 |
| 관찰주소 | 원래 DOM에서 본 주소. blob 주소는 진단용으로만 여기에 기록 |
| URL확보시각(KST) | 다운로드URL 후보를 실제 관찰한 시각. 후보가 없으면 빈 값 |
| 만료추정시각(KST) | 추정 근거가 있는 경우만 기록. 빈 값은 무기한이 아닌 미상 |
| 만료근거 | `oe_hex_unverified` 또는 `unknown`; 공식적으로 확인한 근거가 생기면 구체적으로 기록 |
| 주소상태 | 아래 상태값 |
| 선언 폭(px), 선언 높이(px) | srcset/연결된 자산 정보에 명시된 값만. 파일 검증 값이 아님 |
| 추출위치 | `img.srcset`, `picture.source.srcset`, `img.currentSrc`, `img.src`, `video.currentSrc`, `video.src`, `video.source`, `pageAssets` 등 실제 출처 |
| 비고 | 고해상도 미확보, 첨부 연결 근거, manifest만 관찰 등 한계 |
| 확인실행ID | 해당 미디어 정보를 실제 확인한 실행 ID |

주소 상태:
- `http_candidate`: HTTPS 파일 URL 후보 있음. 인증·만료·실제 다운로드 성공 미검증.
- `blob_unresolved`: blob 관찰, 해당 첨부의 직접 파일 URL 미확보.
- `missing`: 사용 가능한 파일 URL 없음. manifest/segment만 있거나 연결 불확실한 경우도 여기에 사유 기록.

갱신한 URL은 확보 시각·추정 만료·근거·상태를 함께 갱신한다. 이후 재관찰에서 URL을 못 찾았다는 이유만으로 기존 후보를 새 시각으로 재확인 처리하지 않는다. 이전 후보를 보존할 때는 원래 시각과 한계를 유지한다.

### 만료와 향후 실행기 인계

- 미디어 CDN URL에는 만료가 있을 수 있다. **현재 Threads의 모든 링크가 24시간 또는 1~4일 유효하다는 보장은 없다.** [Meta의 CDN URL 만료 관련 설명](https://about.fb.com/news/2020/11/bug-bounty-program-10th-anniversary/)은 만료 동작의 존재를 뒷받침하지만 현재 Threads의 고정 TTL을 정의하지 않는다.
- 일부 URL의 `oe`를 16진 Unix 초로 읽는 방식은 공식 계약으로 확인되지 않은 추정이다. 선택적으로 사용하되 올바른 16진수이고 2000~2100년의 유효한 시각으로 해석될 때만 `oe_hex_unverified`와 함께 저장한다. 다른 경우는 unknown/빈 값이다. 추정 시각 전이라고 다운로드를 보장하거나 이후라고 파일이 반드시 소멸했다고 단정하지 않는다.
- blob URL은 브라우저의 Blob/MediaSource를 참조하며 별도 앱이 나중에 문자열만으로 재사용할 다운로드 URL이 아니다. [MDN blob URL 설명](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob)을 참고한다.
- 로컬 앱은 검증된 결과 Excel을 읽고 후보 URL을 처리한다. 플러그인은 URL을 기록할 뿐 다운로드하지 않는다. 링크를 수주간 축적하면 과거 파일 확보가 실패할 수 있다. 원문URL/ID는 재확인 대상 식별용이지 영구 미디어 접근 보장이 아니다. 만료된 링크 재수집은 별도 요청 범위다.
- 향후 단일 공용 실행기가 소유할 다운로드 시각·파일 경로·성공 여부는 이 수집 양식의 완료 상태와 혼합하지 않는다. Electron은 같은 실행기의 상태를 읽는다. Excel만으로 모든 영상 다운로드가 가능하다고 약속하지 않는다.

## 실행기록

키: `(실행ID, 계정명)`. 신규 수집은 계정 종료 후 확정 실행 행을 한 번 추가하고 이력으로 보존한다. 기존 버전의 미확정 running 행을 복구할 때만 해당 행을 마무리한다. 실행 ID는 시각과 짧은 고유 접미사로 생성하며 계정·게시글 시트와 일치시킨다.

| 열 | 의미 |
|---|---|
| 실행ID, 계정명 | 실행과 계정 식별 |
| 수집일자(KST) | 실행 시작 시 KST 날짜, 시간 없는 Excel 날짜값. 결과 파일명과 일치 |
| 시작(KST), 종료(KST) | 실제 실행 시각, 진행 중 종료는 빈 값 |
| 방식 | `initial` / `incremental` |
| 기존기준ID, 다음기준ID | 실행 전 기준과 성공적으로 저장할 다음 기준 |
| 최하단확인ID | 이번에 수집 대상으로 확인한 마지막 적격 원글. 기준글 자체는 제외 |
| 기준발견 | `Y`, `N`, `NA`(최초) |
| 대상확인수 | 이번 탐색에서 처리한 고유 적격 원글 수. 기존 Excel 행도 포함 |
| 신규저장수 | 이번 실행에서 해당 날짜 파일에 새로 추가한 원글 행 수. 전체 기간 최초 발견 수를 의미하지 않음 |
| 결과 | 아래 상태값 |
| 누락상태 | `not_applicable`, `boundary_reached`, `possible_gap`, `unknown` |
| 특이사항 | 이전 기준 미발견, 캡션/첨부 불완전, 중단 사유 등. 알 수 없는 누락 수량을 만들지 않음 |
| 이전반영실행ID | 실행 시작 시 accounts.xlsx의 최근실행ID. 계정 상태 복구 시 순서 확인용 |

| 결과 | 기준 갱신 |
|---|---|
| `running` | 기존 기준 유지 |
| `initial_complete` | 이번 요청의 최초 수집 대상 중 첫 ID |
| `anchor_reached` | 이번 첫 대상 ID; 대상이 없으면 기존 기준 |
| `cap_reached` | **이번 요청의 목표 건수 중 첫 ID**. 이전 기준 미발견과 possible_gap 기록 |
| `end_reached` | 명시적인 실제 목록 끝. 이번 첫 대상 ID, 대상 없으면 기존 기준. 이전 기준 미발견이면 possible_gap |
| `partial` | 제한/오류/사용자 중단/시간·이동 상한/순서 판정 불가. 기존 기준 유지, 누락상태 unknown |
| `skipped_daily` | 이전 버전의 당일 생략 이력. 새 수집에서는 생성하지 않음 |
| `skipped_invalid` | 계정·URL·기준 상태 불일치. 기존 기준 유지 |

`boundary_reached`는 이번 실행에서 이전 기준까지 확인했다는 의미이며 과거 cap_reached의 누락 가능성을 해소했다는 뜻이 아니다. 완료 조건을 충족해도 더 최근 카드의 원글/미디어 판정이 남아 탐색 연속성을 보장하지 못하면 partial로 처리한다. 캡션 일부나 URL 미확보만으로 적격 판정이 확정된 원글의 기준 갱신을 막지는 않는다.

수집 중에는 `_work` JSONL만 기록한다. 종료 후 helper가 결과 Excel·accounts를 저장·검증한 뒤 임시 기록을 정리한다. 저장 실패 시 전체 중단하고 같은 입력으로 재수집 없이 복구한다. running은 과거 파일 읽기·복구용 상태이며 신규 수집은 종료 또는 partial만 확정한다. 같은 날짜 재실행에서도 이전 실행 행과 누락 경고를 보존한다.

helper는 실행기록의 추가 열 `수집입력SHA256`으로 정확한 재시도를 확인한다. 게시글의 추가 열 `캡션원본확인시각(KST)`, `캡션원본실행ID`, `최근관찰첨부 상태`는 같은 날 부분 관찰로 이전 완전 캡션을 유지할 때 확인 시각과 실제 최신 첨부 상태를 구분한다. 이전 daily-v1 파일에 이 열이 없어도 읽을 수 있다. 사용자 추가 열·메모·서식과 별도 ZIP 파트는 보존한다.
